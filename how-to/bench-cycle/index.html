    플러그인 변경 평가하기 (bench)¶

    한 줄 요약

    스킬·에이전트 파일을 고쳤을 때, 그 에이전트가 쓰는 문서 (plan.md · .plan.critic.md · .eval.md) 가 정말 좋아졌는지를 같은 잣대로 두 번 재서 숫자로 비교합니다. 채점은 서로 모르는 채점자 셋이 하고, 좋아졌는지는 도구가 셉니다. 사람은 무엇을 잴지 · 적용할지 · 채택할지 세 가지를 정합니다.

    evaluator 는 코드를, bench 는 에이전트가 쓴 문서를 평가합니다. 코드가 요구사항을 충족하는지는 여기서 보지 않습니다 (@ag-evaluator·@ag-code-reviewer 의 몫).

    이 문서를 읽는 법¶

    언제 쓰나¶

    • agents/ag-*.md·skills/*/SKILL.md 를 고치는 PR 에 「좋아졌다」 의 근거를 붙이고 싶을 때
    • 읽는 양을 줄이는 변경 (다이어트·슬라이스) 이 산출물 품질을 떨어뜨리지 않았는지 확인할 때
    • 지금 판의 에이전트가 어떤 결함을 반복하는지 측정만 하고 싶을 때

    평소 feature 작업에는 쓰지 않습니다. 스킬도 훅도 아니라서, 누가 명령을 치기 전에는 아무 일도 일어나지 않습니다.

    등장인물¶

    누구 무엇을 하나
    사람 (당신) 무엇을 잴지 정하고, 질문 한 줄을 쓰고, 「적용」 과 「채택·되돌림」 을 결정한다. 이 셋은 다른 누구도 대신하지 않는다
    메인 세션 소비 레포 (예: nimda) 에서 연 Claude Code 세션. 도구 명령을 치고, 채점자를 부르고, 개선 계획 초안을 쓴다
    채점자 @ag-bench-scorer × 3 정해진 파일만 읽고 축마다 1~5점과 근거 좌표를 매긴다. 서로의 결과도, 변경 전인지 후인지도 모른다
    도구 bench-cycle.py 단계를 넘길 조건을 세고, 사본을 뜨고, 전후 차이를 계산한다. 「좋아졌다」 는 도구만 말한다

    두 가지 쓰임¶

    A. 측정만 B. 개선 사이클 (전후 비교)
    묻는 것 지금 판이 어떤 결함을 반복하나 이 변경으로 좋아졌나
    단계 1 → 5 1 → 11
    사람의 결정 무엇을 잴지 · 질문 + 적용할지 · 채택할지
    끝 stop (측정 전용) close (채택 또는 되돌림)

    A 로 시작해 결함이 보이면, 같은 사이클을 그대로 B 로 이어 가도 됩니다 (before 채점을 다시 하지 않아도 됩니다).

    한눈에 보기¶

    단계 목적 사람이 하는 일 확인할 결과
    1. 사이클 열기 무엇을, 어느 표본으로, 어느 잣대로 잴지 고정 대상 에이전트·표본·축을 고른다 사이클 번호 · 표본 사본 · 다음 안내
    2. 표본 만들기 (run) 지금 판으로 산출물을 분리된 곳에서 새로 낸다 실행 명령을 돌린다 (또는 메인 세션에 맡긴다) 새 산출물 수 · 실제 파일 변경 경고 없음
    3. 질문 확정 채점자가 받는 질문 한 줄을 굳힌다 「확인하려는 것」 을 쓴다 brief 에 질문 한 줄만 실렸는지
    4. 채점 서로 모르는 채점자 셋이 점수를 매긴다 채점자 셋을 부른다 (프롬프트에 아무것도 덧붙이지 않는다) ingest 통과 · 축별 평균 · 불일치 · 발견
    5. 결과 읽기 반복되는 결함을 찾는다 발견 표를 읽고 다음을 정한다 두 명 이상이 따로 잡은 결함
    6. 개선 계획 발견 → 무엇을 고칠지 계획을 검토한다 planned 통과 · 바꿀 파일 목록
    7. 적용 계획한 파일만 고쳐 커밋 「적용」 을 승인한다 (답 원문) 계획 밖 파일 0 · 적용 커밋 판
    8. 다시 표본 바뀐 판으로 같은 입력 을 다시 돌린다 실행 명령을 돌린다 새 산출물 · before 와 다른 내용
    9. 다시 채점 같은 잣대로 다시 잰다 채점자 셋을 다시 부른다 ingest 통과
    10. 대조·결정 전후 차이를 도구가 세고 사람이 정한다 「채택·되돌림」 을 결정한다 (답 원문) 판정 낱말 · 오른·내린 축 · 발견 수 변화
    11. 출하 채택한 변경을 내보낸다 PR 을 머지한다 PR 본문에 대조 결과 인용

    모든 명령의 응답 끝에 다음 이 있습니다. 그대로 복사해 다음 명령으로 쓰면 됩니다 (실행한 도구의 절대 경로로 찍힙니다).

    시작 전 준비¶

    채점은 소비 레포 세션에서

    채점자는 자기를 부른 세션의 프로젝트 메모리를 함께 받습니다. 플러그인 레포 세션의 메모리에는 이전 사이클 판정이 쌓이기 쉬워, 그 세션에서 부르면 채점자가 「지난번엔 이 축이 내려갔다」 를 미리 알고 채점합니다. 그래서 사이클 전체를 소비 레포 (예: nimda) 세션에서 돌립니다. 플러그인 파일을 고쳐 커밋하는 일 (7단계) 만 플러그인 레포에서 합니다.

    • 설치본을 최신으로 맞추고 세션을 새로 엽니다. 사이클은 처음 연 도구의 판을 기억하고, 채점자가 다른 판의 도구를 부르면 거절합니다. 사이클 도중에는 플러그인을 갱신하지 않습니다.

    • 도구 경로 — 아래 명령의 {BC} 는 설치본 도구입니다. 명령은 소비 레포 루트 (workspace/ 가 보이는 곳) 에서 칩니다.

      {BC} = python3 ~/.claude/plugins/cache/deali-skills/dp-skills/{설치 버전}/tools/bench-cycle.py

    • 플러그인 레포 경로 — 표본을 새로 내거나 (run 모드) 적용 커밋을 대조할 때 --plugin-repo {플러그인 레포} 가 필요합니다. 그 세션이 플러그인 레포에 쓸 수 있어야 하므로 디렉터리를 추가해 둡니다 (/add-dir).

    • run 모드의 실행 명령은 새 claude 프로세스입니다 — 로그인이 만료됐으면 먼저 claude auth login.

    단계별 안내¶

    1. 사이클 열기 — init¶

    목적. 무엇을 (대상 에이전트), 어느 표본으로, 어느 잣대 (채점 축) 로 잴지를 사이클에 고정합니다. 여기서 정한 것은 사이클 끝까지 갑니다 — 도중에 잣대가 바뀌면 전후 비교가 무효가 되기 때문입니다.

    사람이 하는 일.

    • 대상: 어느 에이전트의 산출물을 잴지. 처음이라면 @ag-planner-critic (critic) 이 효과가 잘 보입니다.
    • 표본 얻는 길:
      • run (권장) — 입력 (critic 이면 plan, planner 면 명세) 을 주면 도구가 분리된 곳에서 산출물을 새로 냅니다. 같은 입력으로 전후를 비교할 수 있고 실제 파일을 건드리지 않습니다.
      • replay — 이미 있는 산출물을 그대로 채점합니다. 측정만 할 때 편하지만, after 표본은 바뀐 판이 자연히 새로 쓸 때까지 기다려야 합니다.
    • 표본 수: 2~5건. 많을수록 정확하지만 채점 비용이 늘어납니다.
    • 축: critic 이면 보통 Q1,Q3,Q4,Q6,Q8,P1. 축의 뜻은 아래 「결과 읽는 법」.
    {BC} init --slug critic-generalization \
  --subject "0.44.2 이후 critic 규칙이 다른 plan 에서도 지켜지는가" \
  --run critic --inputs {plan 경로들} --context {명세 경로들} \
  --subject-files dp-skills/agents/ag-planner-critic.md \
  --axes Q1,Q3,Q4,Q6,Q8,P1 --plugin-repo {플러그인 레포}

    replay 는 --run·--inputs 대신 --artifacts {산출물 경로들} 을 줍니다.

    확인할 결과.

    • id — 사이클 번호 (예: 003). 이후 모든 명령에 씁니다.
    • run.outputs — 새로 낼 산출물 경로. 예상한 feature 가 맞는지.
    • plugin_version_before — 지금 판. 측정의 기준입니다.
    • workspace/{TEAM}/bench/003-…/ 폴더가 생기고 입력·명세가 사본으로 들어갑니다.

    2. 표본 만들기 — sandbox → 실행 → collect (run 모드만)¶

    목적. 지금 판의 에이전트로 산출물을 실제 프로젝트와 분리된 곳에서 새로 냅니다. 소비 레포에서 에이전트를 직접 다시 부르면 실제 산출물이 덮어쓰입니다 — 이 단계가 그걸 막습니다.

    사람이 하는 일.

    1. 분리 트리를 만듭니다.

      {BC} sandbox --id 003 --phase before

    2. 응답의 인증 확인 명령을 먼저 돌립니다 (아무것도 안 나오면 정상).

    3. 실행 의 명령들을 돌립니다. 표본 하나에 opus 로 7~10분, 서로 독립이라 동시에 돌려도 됩니다. 메인 세션에 「실행 명령을 돌려 줘」 라고 맡겨도 됩니다.

      화면에서 복사하지 말 것

      일부 화면은 응답 JSON 의 >·& 를 &gt;·&amp; 로 바꿔 보여 주고, 긴 줄 중간에 공백을 끼웁니다. 그대로 복사하면 명령이 깨집니다. 터미널 원문에서 복사하거나 메인 세션에 맡깁니다.

    4. 다 끝나면 거둡니다.

      {BC} collect --id 003 --phase before

    확인할 결과.

    • samples — 표본 수가 입력 수와 같은가.
    • 실제 산출물 변경 (경고) — 비어 있어야 합니다. 무언가 있으면 분리가 깨졌거나 그 사이 사람이 실제 파일을 고친 것입니다.
    • 대상 밖 프로젝트 파일 변경 — 보통 비어 있습니다. 에이전트가 다른 파일을 건드렸다는 신호입니다.
    • 「분리 트리에 새 산출물이 없습니다」 로 거절되면 실행이 실패한 것입니다. 응답에 나온 run-N.log 를 봅니다.
    • 다 쓴 분리 트리는 {BC} sandbox-remove --id 003 --phase before 로 지웁니다.

    3. 질문 확정 — scenario.md § 3 → brief¶

    목적. 채점자가 받는 질문 한 줄을 정하고, 채점자가 읽어도 되는 파일 목록 (허용 목록) 과 잣대를 굳힙니다. 채점자는 이 사이클이 무엇을 기대하는지 (성공 조건) 도, 변경 전인지 후인지도 모릅니다 — 기대를 아는 채점은 그쪽으로 기울기 때문입니다.

    사람이 하는 일. 사이클 폴더의 scenario.md 끝 ## 3. 기대 를 자기 말로 채웁니다.

    ## 3. 기대

- 확인하려는 것: (채점자가 받는 유일한 질문 — 결함 범주를 구체적으로)
- 성공: (B 만 — 어느 축이 0.3 이상 오르면 채택인가 · A 는 「해당 없음」)
- 되돌림: (B 만 — 어느 축이 내려가면 되돌리나)

    좋은 질문은 찾을 결함을 이름으로 적습니다. 예: 「① 챌린지 하나에 원인 하나만 담는가 ② suggestion 으로 낮출 때 이유를 적는가 ③ 따옴표 인용이 plan 원문에 있는가」. 「잘 썼나」 같은 질문은 점수만 흔들립니다.

    {BC} brief --id 003 --phase before

    확인할 결과.

    • brief-{라벨}.md 가 생깁니다 (라벨은 8edk 같은 무작위 이름 — 단계를 가립니다).
    • 그 파일의 「이 사이클이 묻는 것」 에 질문 한 줄만 있고, before·after·「성공」 이라는 말이 없는지.
    • allow — 표본·참조·채점표·지시 파일 수. 표본 3건이면 보통 10~12개.
    • 이 뒤로 scenario.md 를 고치면 그 사이클은 끝까지 갈 수 없습니다 (해시로 굳었습니다). 질문을 바꾸려면 stop 하고 새 사이클을 엽니다.

    4. 채점 — 채점자 셋 → ingest¶

    목적. 서로 모르는 채점자 셋이 같은 표본을 따로 채점합니다. 한 사람의 점수는 잡음이라 셋의 평균을 씁니다.

    사람이 하는 일. 소비 레포 세션에서 셋을 부릅니다. 한 메시지로 보내도, 하나씩 보내도 됩니다. 세션은 하나면 됩니다 — 부를 때마다 새 맥락의 채점자가 뜹니다.

    @ag-bench-scorer 사이클 003 · 채점자 1
@ag-bench-scorer 사이클 003 · 채점자 2
@ag-bench-scorer 사이클 003 · 채점자 3

    프롬프트에 아무것도 덧붙이지 않습니다. 「#17 이 약할 거야」 한 줄도 채점을 기울게 합니다. 채점자마다 몇 분씩 걸립니다. 셋이 끝나면 수합합니다.

    {BC} ingest --id 003 --phase before

    확인할 결과.

    • 통과 — 응답에 summary 가 나옵니다 (다음 단계에서 읽습니다). 채점 요약 scores/{라벨}.json 과 정량 지표 metrics-{라벨}.json 이 생깁니다.
    • 거절 — 사유가 줄마다 나옵니다. 「허용 목록 밖을 읽음」·「축 누락」·「좌표 없음」 이면 그 번호의 채점자만 새로 다시 부릅니다 (파일은 덮어씁니다).

    5. 결과 읽기¶

    목적. 숫자보다 반복되는 결함을 찾습니다. 다음에 무엇을 고칠지의 재료입니다.

    사람이 하는 일. 세 군데를 봅니다.

    1. 축별 평균 (summary.axes.{축}.mean) — 3점대 이하인 축이 약점입니다. disagree: true 인 축은 채점자끼리 2점 이상 갈렸다는 뜻이라 평균을 믿지 않습니다.
    2. 발견 수 (summary.findings — Blocker · Major · Minor) — Major 가 많으면 읽는 사람이 되물어야 하는 결함이 많다는 뜻입니다.
    3. 채점 파일의 ## 2. 발견 표 (scores/{라벨}-1.md~-3.md) — 두 명 이상이 따로 잡은 결함이 진짜입니다. 한 명만 잡은 것은 취향일 수 있습니다. 각 채점 파일의 ## 0. 요약 에 그 채점자가 본 「가장 큰 결함」 이 한 줄로 있습니다.

    다음을 정합니다.

    • 측정만 (A) — 반복 결함을 기록하고 닫습니다: {BC} stop --id 003 --reason "측정 전용".
    • 개선 (B) — 반복 결함을 고칠 계획으로 6단계.

    6. 개선 계획 — plan.md → planned (B)¶

    목적. 「무엇이 약했나」 를 「어느 파일을 어떻게 고치나」 로 바꿉니다. 계획은 before 점수를 보고 쓰므로 블라인드 대상이 아닙니다.

    사람이 하는 일. 메인 세션에 「발견 표로 개선 계획 초안을 써 줘」 라고 맡기고, 초안을 검토합니다. 사이클 폴더의 plan.md 는 절 다섯입니다.

    절 내용
    ## 0. 요약 한 단락
    ## 1. 발견 → 변경 어느 발견을 어떤 변경으로 다루나 (다루지 않는 것도)
    ## 2. 변경 집합 바꿀 파일 · 무엇을 · 기대 축 표 — 첫 칸은 플러그인 레포 경로 (예: dp-skills/agents/ag-planner-critic.md)
    ## 3. 기대 효과 축별 방향·크기. 모든 축이 오른다는 계획은 계획이 아닙니다 — 무엇을 잃을 수 있는지도 적습니다
    ## 4. 되돌리기 되돌리는 방법 
    {BC} planned --id 003

    확인할 결과. plan_files (바꿀 파일 목록) 가 의도와 같은지, 「대상 밖」 칸이 비어 있는지. 계획을 고치면 planned 를 다시 돌리면 됩니다.

    7. 적용 — 「적용」 답 → 플러그인 가지 커밋 → applied (B)¶

    목적. 계획한 파일만 고쳐 커밋하고, 그 커밋을 사이클에 기록합니다.

    사람이 하는 일.

    1. 「적용해」 같은 자기 답을 원문 그대로 사이클 폴더 inputs/001-answer-apply.md 에 둡니다. 요약하지 않습니다 — 이 파일이 승인의 증거입니다.
    2. 플러그인 레포에서 main 으로부터 가지를 따고, 변경 집합의 파일만 고쳐 커밋합니다.

    3. 기록합니다.

      {BC} applied --id 003 --commit {SHA} --answer-file {사이클 폴더}/inputs/001-answer-apply.md

    확인할 결과.

    • 계획 밖 변경 — 비어 있어야 합니다. 섞이면 거절됩니다 (계획을 고쳐 planned 를 다시 돌리거나, 확인했으면 --allow-extra).
    • 계획에 있는데 안 바뀐 파일 — 빠뜨린 게 없는지.
    • plugin_version_after — 적용 커밋의 판.

    8. 다시 표본 — sandbox --phase after → 실행 → collect (B)¶

    목적. 바뀐 판의 에이전트로 같은 입력을 다시 돌립니다. 입력은 1단계 때의 사본이라, 그 사이 실제 plan 이 고쳐졌어도 전후가 같은 입력을 받습니다.

    사람이 하는 일. 2단계와 같습니다. --phase after 로 바꿔 돌립니다.

    확인할 결과. 2단계와 같고, 하나가 더 있습니다 — before 와 내용이 같으면 거절합니다 (바뀐 판이 같은 결과를 냈다는 뜻이라 비교할 것이 없습니다).

    9. 다시 채점 — brief --phase after → 채점자 셋 → ingest (B)¶

    목적. 3~4단계를 같은 잣대로 반복합니다. 채점자는 이것이 두 번째 채점인 줄 모릅니다 (라벨이 다릅니다).

    사람이 하는 일. {BC} brief --id 003 --phase after (run 모드는 --artifacts 없이) → 4단계와 같은 방식으로 채점자 셋 → {BC} ingest --id 003 --phase after.

    확인할 결과. 4단계와 같습니다. 「시나리오·채점표가 before 때와 다릅니다」 로 거절되면 그 사이 scenario.md 가 바뀐 것입니다 — 새 사이클입니다.

    10. 대조와 결정 — compare → 「채택·되돌림」 답 → decide → close (B)¶

    목적. 전후 차이를 도구가 세고, 사람이 채택할지 정합니다.

    {BC} compare --id 003

    확인할 결과. compare.md 의 ## 0. 판정 한 단락.

    판정 뜻 보통의 결정
    improved 오른 축만 있다 채택
    regressed 내린 축만 있다 되돌림 (단, 내린 폭이 잡음 범위인지 본다)
    mixed 오른 축과 내린 축이 함께 있다 시나리오가 겨냥한 축이 올랐고 발견 수가 줄었으면 채택 검토
    unchanged 움직인 축이 없다 「효과 없음」 이 아니라 「이 표본으로는 못 가른다」 — 표본을 늘려 새 사이클

    함께 볼 것: 겨냥한 축이 올랐나 · Major 발견 수가 줄었나 · ## 2. 정량 지표 의 분량 변화 · 린트 경고 변화. 한 축의 ±0.5 는 잡음일 수 있습니다 (아래 「결과 읽는 법」).

    사람이 하는 일. 결정을 적용 답과 다른 파일에 원문으로 둡니다 (inputs/002-answer-decide.md) — 적용 승인이 채택 승인이 아니기 때문입니다.

    {BC} decide --id 003 --result adopt --answer-file {사이클 폴더}/inputs/002-answer-decide.md

    {BC} close --id 003

    되돌림이면 --result revert → 플러그인 레포에서 git revert {적용 커밋} → close --id 003 --note {되돌린 커밋 SHA}.

    11. 출하 (B)¶

    목적. 채택한 변경을 플러그인 릴리스로 내보냅니다.

    사람이 하는 일. 적용 가지로 PR 을 열고, 본문에 compare.md § 0 을 그대로 인용합니다. 이후는 평소 릴리스 절차입니다.

    결과 읽는 법¶

    채점 축¶

    산출물 축 (Q) 은 다음 독자에게 쓸모 있는가, 과정 축 (P) 은 지시를 지켰는가를 봅니다. 척도는 5 본보기 · 4 작은 흠 · 3 섞임 · 2 뚜렷한 결함 · 1 역할 실패.

    축 critic 기준으로 묻는 것
    Q1 소비자 적합성 planner 가 챌린지만 보고 무엇을 고칠지 아는가
    Q2 구체성 제안이 「재확인」 인지 「변경 요구」 인지 분명한가
    Q3 일관성 인용한 단계·줄 범위가 plan 과 맞는가 · severity 가 본문과 같은가
    Q4 추적성 인용한 plan 단계·절이 실제로 있는가
    Q6 밀도 챌린지끼리 겹치거나 일반론이 있는가
    Q8 크기 챌린지 수가 plan 크기에 맞는가 · 취향을 blocking 으로 올렸는가
    P1 지시 준수 wrapper 가 요구한 필드·합의표·형식을 지켰는가

    plan·eval 기준 질문과 P3 (경계) 은 채점표 원본 (skills/context/shared/bench-rubric.md) 에 있습니다.

    숫자를 읽을 때 주의할 것¶

    • 잡음의 크기. 같은 파일·같은 질문을 다른 채점자 쌍이 다시 재자 축 평균이 평균 0.33, 최대 1.0 달랐습니다. 그래서 채점자가 셋이고, 도구는 ±0.3 안의 차이를 「같음」 으로 셉니다. 한 축의 ±0.5 하나로 결론을 내리지 않습니다.
    • 발견 수를 함께 봅니다. 점수가 같아도 Major 가 7 → 2 로 줄었다면 의미 있는 변화입니다.
    • 표본이 다르면 분량 비교는 뜻이 없습니다. 정량 지표의 글자 수 차이는 같은 입력 (run 모드) 일 때만 읽습니다.

    분리 트리에 새 산출물이 없습니다 실행이 실패했다 (로그인 만료 등) 응답의 run-N.log 를 보고 다시 실행
    허용 목록 밖 / 금지 경로를 읽음 채점자가 정해진 파일 밖을 열었다 그 번호의 채점자만 새로 다시 부른다
    시나리오·채점표가 before 때와 다릅니다 brief 뒤에 scenario.md 를 고쳤다 stop 하고 새 사이클
    after 표본이 before 표본과 내용이 같습니다 바뀐 판이 같은 결과를 냈다 변경이 그 산출물에 영향을 주는지 다시 본다
    계획 밖 파일이 바뀌었습니다 적용 커밋에 계획에 없는 파일이 섞였다 계획을 고쳐 planned 재실행, 또는 확인 뒤 --allow-extra
    적용 커밋이 계획의 파일을 하나도 바꾸지 않았습니다 다른 커밋을 넘겼다 커밋 SHA 확인

    무엇이 「블라인드」를 지키나¶

    선 지키는 장치 어기면
    기대를 모르고 채점한다 단계마다 무작위 라벨 · 지시에 질문 한 줄만 · scenario.md 는 허용 목록 밖 시나리오를 읽은 채점은 받지 않는다
    정해진 것만 읽는다 brief 가 목록을 적고 ingest 가 채점 파일의 inputs: 와 대조 그 채점은 받지 않는다
    전후는 같은 잣대 시나리오·채점표 해시 · 잣대 값 · 도구 판을 사이클 시작 때 굳힌다 after 를 받지 않는다
    눈은 셋 서로 다른 채점자 셋 · 2점 이상 갈리면 「불일치」 모자라면 받지 않는다
    숫자는 도구가 compare 만 전후를 가른다 사람·에이전트가 「좋아졌다」 고 쓰지 않는다
    결정은 답 원문 적용·채택 답을 각각 다른 파일로 요구 받지 않는다
    실제 산출물은 건드리지 않는다 run 모드의 분리 트리 · collect 의 변경 경고 경고

    못 지키는 것 — 채점자의 inputs: 는 자기 신고이고, 부른 세션의 메모리는 도구가 볼 수 없습니다. 그래서 채점자가 셋이고, verify-blind 가 받은 채점을 다시 대조하며, 거점을 소비 레포 세션으로 정해 둡니다.
