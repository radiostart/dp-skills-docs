    플러그인 변경 전후 채점하기¶

    한 줄 요약

    스킬·에이전트 파일을 고친 뒤, 그 산출물 (plan.md · .plan.critic.md · .eval.md) 이 정말 좋아졌는지를 같은 잣대로 두 번 재서 채택·되돌림을 정합니다. evaluator 는 코드를, bench 는 에이전트가 쓴 문서를 평가합니다.

    언제 쓰나¶

    • agents/ag-*.md·skills/*/SKILL.md 를 고치는 PR 에 "좋아졌다" 의 근거를 붙이고 싶을 때
    • 다이어트·슬라이스처럼 읽는 양을 줄이는 변경이 산출물 품질을 떨어뜨리지 않았는지 확인할 때
    • 같은 산출물에 대한 두 판 (예: critic 규칙 개정 전후) 을 느낌이 아니라 숫자로 비교할 때

    코드가 요구사항을 충족하는지는 여기서 보지 않습니다 — 그것은 @ag-evaluator 와 @ag-code-reviewer 의 몫입니다.

    전제¶

    • 소비 레포에 workspace/TEAM.md 가 있고, 채점할 산출물이 workspace/{TEAM}/projects/** 에 있을 것 (replay — 이미 만들어진 산출물을 채점)
    • 플러그인 dev 체크아웃 (git) 의 경로를 알 것 — applied 가 적용 커밋의 diff 를 봅니다. --plugin-repo 인자 또는 workspace/_common/config.md ## 언어·도구 기본값 표의 bench_plugin_repo
    • 채점자 (@ag-bench-scorer) 를 둘 부를 수 있을 것 — 한 채점자의 점수는 잡음입니다

    한 바퀴¶

    init ──brief──▶ @ag-bench-scorer ×2 ──ingest──▶ before
  │                                                │
  └ 표본 사본 · 채점표 사본 · scenario § 3 기대       plan.md (사용자·메인 세션) ──planned──▶ planned
                                                   │
          사용자 「적용」 답 원문 (inputs/) ──▶ 플러그인 가지에서 변경 집합 적용·커밋 ──applied──▶ applied
                                                   │
          바뀐 플러그인으로 새 산출물 ──brief --phase after──▶ @ag-bench-scorer ×2 ──ingest──▶ after
                                                   │
                                 compare (도구가 센다) ──▶ compared ──▶ 사용자 「채택·되돌림」 답 원문 ──decide──▶ close

    한 호출이 한 단계입니다. 모든 명령의 응답에 다음 이 있습니다 — 그대로 따라가면 됩니다.

    절차¶

    아래 명령은 소비 레포 루트 (workspace/ 가 보이는 곳) 에서 실행합니다. {PLUGIN} 은 설치된 플러그인 경로 (${CLAUDE_PLUGIN_ROOT} 또는 ~/.claude/plugins/cache/deali-skills/dp-skills/{버전}).

    1. 사이클 열기 — init¶

    무엇을 잴지 먼저 정합니다: 표본 (산출물 2~5건) · 참조 (산출물이 가리키는 상위 문서 — critic 을 채점하면 그 plan 과 명세) · 대상 파일 (개선 계획이 고칠 플러그인 파일) · 축.

    python3 {PLUGIN}/tools/bench-cycle.py init \
  --slug critic-quality \
  --subject "@ag-planner-critic 의 챌린지가 planner 에게 쓸모 있는 입력인가" \
  --artifacts workspace/dp-team/projects/p1/features/03-x.plan.critic.md workspace/dp-team/projects/p1/features/05-y.plan.critic.md \
  --context  workspace/dp-team/projects/p1/features/03-x.md workspace/dp-team/projects/p1/features/03-x.plan.md \
             workspace/dp-team/projects/p1/features/05-y.md workspace/dp-team/projects/p1/features/05-y.plan.md \
  --subject-files dp-skills/agents/ag-planner-critic.md \
  --axes Q1,Q3,Q4,Q6,Q8,P1 \
  --plugin-repo ~/Projects/deali-skills-plugin \
  --workspace workspace

    workspace/{TEAM}/bench/001-critic-quality/ 가 생기고 표본·참조·대상 파일이 samples/ 에 복사됩니다 — 원본은 재호출 때 덮어쓰이므로 좌표는 사본 기준입니다. 그다음 scenario.md § 3 기대 를 자기 말로 채웁니다: 확인하려는 것 · 어느 축이 오르면 성공 · 어느 축이 내리면 되돌림. 비워 두면 채점자가 무엇을 묻는지 모릅니다.

    2. before 채점 — brief → 채점자 둘 → ingest¶

    python3 {PLUGIN}/tools/bench-cycle.py brief --id 001 --phase before --workspace workspace

    허용 목록 (brief-before.md) 이 굳고 시나리오·채점표 해시가 고정됩니다. 그다음 메인 세션에서 채점자를 따로 두 번 부릅니다. 프롬프트는 이 둘뿐입니다 — 산출물 요약·"어디가 약하다"·다른 채점자의 결과를 넣지 않습니다 (앵커).

    @ag-bench-scorer 사이클 001 · 채점자 1
@ag-bench-scorer 사이클 001 · 채점자 2

    둘이 끝나면:

    python3 {PLUGIN}/tools/bench-cycle.py ingest --id 001 --phase before --workspace workspace

    거절되면 (허용 목록 밖을 읽음 · 축 누락 · 좌표 없음 · 채점자 부족) 그 채점자만 같은 번호로 새 맥락에서 다시 부릅니다 (파일은 덮어씁니다). 통과하면 scores/before.json (평균·불일치) 과 metrics-before.json (정량 지표 + 린트) 이 생깁니다.

    3. 개선 계획 — plan.md → planned¶

    scores/before.json 과 두 채점 파일의 ## 2. 발견 을 읽고 사이클 폴더에 plan.md 를 씁니다 (사용자 또는 메인 세션 — 계획은 before 점수를 봐야 하므로 블라인드 대상이 아닙니다). 절 다섯: ## 0. 요약 · ## 1. 발견 → 변경 · ## 2. 변경 집합 (| 파일 | 무엇을 | 기대 축 | — 첫 칸은 플러그인 레포 상대 경로, 예 dp-skills/agents/ag-planner-critic.md) · ## 3. 기대 효과 (축별 방향·크기 — 모든 축이 오른다는 계획은 계획이 아닙니다) · ## 4. 되돌리기.

    python3 {PLUGIN}/tools/bench-cycle.py planned --id 001 --workspace workspace

    4. 적용 — 답 원문 → 플러그인 가지에서 커밋 → applied¶

    사용자의 「적용」 답을 원문 그대로 inputs/001-answer-apply.md 에 둡니다 (요약 금지). 플러그인 레포에서 main 으로부터 가지를 따고 변경 집합의 파일만 고쳐 커밋합니다. 그다음:

    python3 {PLUGIN}/tools/bench-cycle.py applied --id 001 --commit {SHA} \
  --answer-file workspace/dp-team/bench/001-critic-quality/inputs/001-answer-apply.md --workspace workspace

    도구는 가지가 main 에서 갈라진 자리부터의 diff 를 계획과 대조합니다 — 계획 밖 파일이 섞이면 거절 (사용자가 확인했으면 --allow-extra), 계획 파일을 하나도 안 바꿨으면 거절. 적용 커밋의 plugin.json 버전이 상태에 적힙니다.

    5. after 채점 — 새 산출물 → brief --phase after → 채점자 둘 → ingest¶

    바뀐 플러그인으로 같은 종류의 산출물을 새로 만듭니다 — 예: 그 가지를 claude --plugin-dir ~/Projects/deali-skills-plugin/dp-skills 로 띄워 같은 feature 의 critic 을 다시 돌리거나, 그 버전을 설치한 뒤 다음 feature 의 사이클을 돕니다. 같은 경로라도 내용이 바뀐 파일이면 됩니다 (내용이 같으면 거절).

    python3 {PLUGIN}/tools/bench-cycle.py brief --id 001 --phase after \
  --artifacts workspace/dp-team/projects/p1/features/03-x.plan.critic.md --workspace workspace

    채점자 둘 (사이클 001 · 채점자 1·2) → ingest --phase after. 시나리오·채점표를 그 사이 고쳤으면 after 를 받지 않습니다 — 새 사이클입니다.

    6. 대조·결정 — compare → 답 원문 → decide → close¶

    python3 {PLUGIN}/tools/bench-cycle.py compare --id 001 --workspace workspace

    compare.md § 0 이 판정 낱말 (improved · regressed · mixed · unchanged) 과 올라간·내려간 축을 냅니다 — 사람·에이전트가 "좋아졌다" 를 쓰지 않습니다. mixed·unchanged 는 「효과 없음」이 아니라 「이 표본으로는 못 가른다」 입니다.

    채택이면 답 원문을 inputs/002-answer-decide.md 에 두고 decide --result adopt → close. 플러그인 PR 본문에 compare.md § 0 을 그대로 인용합니다. 되돌림이면 decide --result revert → 플러그인 레포에서 git revert {적용 커밋} → close --note {되돌린 SHA}.

    무엇이 「블라인드」를 지키나¶

    선 지키는 장치 어기면
    자기가 쓴 것을 채점하지 않는다 채점자는 산출물을 쓴 wrapper 와 다른 에이전트 · 메인 세션이 따로 부른다 · 프롬프트는 「사이클 · 번호」둘뿐 (사람 규약 — 도구가 못 본다)
    허용 목록 밖을 읽지 않는다 brief 가 목록을 적고 ingest 가 채점 파일의 inputs: 를 대조 — 다른 채점·계획·대조·지표·답·상태 · 다른 사이클 · 대화 기록 · 원본 (사본만) · 하류 산출물은 항상 금지 그 채점은 받지 않는다 → 같은 번호로 새 맥락에서 다시
    전후는 같은 잣대 시나리오·채점표 해시가 before 때 굳고 after 가 대조 · scorers·noise_band·disagree_gap 도 init 때 굳는다 after 를 받지 않는다 — 새 사이클
    눈은 둘 단계마다 서로 다른 채점자 ≥ 2 · 같은 축에서 2점 이상 벌어지면 「불일치」 1명이면 받지 않는다 · 불일치 축의 평균은 믿지 않는다
    숫자는 도구가 compare 만 전후를 가른다 (±0.3) 메인 세션·에이전트가 「좋아졌다」고 쓰지 않는다
    적용·채택은 답 원문 applied·decide 가 inputs/ 의 원문 파일을 요구 · 적용 답과 결정 답은 다른 파일 받지 않는다
    계획 밖은 고치지 않는다 applied 가 적용 커밋을 변경 집합과 대조 — 계획 밖 파일이 섞이면 거절 (사용자 확인 뒤 --allow-extra) 거절

    못 지키는 것 — 채점자의 inputs: 는 자기 신고입니다. 허용 목록 밖을 읽고 적지 않으면 도구는 모릅니다. 그래서 채점자가 둘이고 (서로 다른 맥락이 같은 오염을 겪을 확률이 낮습니다), verify-blind 가 받은 채점을 지금 허용 목록으로 다시 대조합니다.

    흔한 실수¶

    • 채점자에게 힌트를 준다. "Q6 이 약할 거야" 한 줄이 앵커입니다. 프롬프트는 사이클 ID 와 번호뿐입니다.
    • 원본을 채점한다. 허용 목록에는 samples/ 사본만 있습니다. projects/** 원본은 그 사이 재호출로 덮어쓰였을 수 있어 좌표가 어긋납니다.
    • after 표본이 before 와 같은 파일이다. 바뀐 플러그인이 새로 만든 산출물이어야 전후입니다 — 내용이 같으면 도구가 거절합니다.
    • 시나리오를 고치고 같은 사이클을 계속한다. 해시가 굳어 있습니다. 묻는 것이 바뀌었으면 stop 하고 새 사이클을 엽니다.
    • 한 축의 ±0.5 를 결론으로 읽는다. 같은 파일을 다른 채점자 쌍이 다시 재자 축마다 0.5~1.0 씩 달랐습니다 (실사용 사이클 실측 · 시나리오 질문이 바뀐 영향과 섞여 있음). 잡음 띠 ±0.3 은 판정 낱말을 가르는 기준일 뿐입니다 — 여러 축이 같은 방향으로 움직였는지, 발견 건수가 함께 줄었는지를 같이 봅니다.
    • mixed·unchanged 를 "효과 없음" 으로 읽는다. 표본 2~5건·채점자 2명의 측정은 거칩니다 — 표본을 늘려 새 사이클을 여는 것이 답입니다.
    • 설정 값을 사이클 도중 바꾼다. bench_* 키를 바꿔도 진행 중 사이클은 init 때 굳힌 값으로 끝까지 갑니다.
    • after 의 과정 축을 변경 전 wrapper 와 대조한다. P 축은 그 산출물을 만든 판의 규칙으로 잽니다. applied 가 적용 커밋의 대상 파일을 samples/plugin-after/ 로 떠서 after 허용 목록에 넣습니다 — 옛 판과 대조하면 새 규칙을 지킨 줄이 「템플릿에 없는 줄」로 깎입니다.
    • 채점자가 다른 단계 표본의 크기를 본다. ls·wc 로 줄 수만 봐도 전후 분량이 드러나 앵커가 됩니다. 사이클 폴더 안에서는 허용 목록 밖 파일의 이름·크기도 보지 않습니다 (inputs: 에 남지 않아 도구가 못 잡습니다 — 채점자 규칙입니다).
    • critic 을 채점하는데 참조 plan 이 개정본이다. planner 가 critic 을 반영하면 plan.md 가 제자리에서 바뀌므로, 그 뒤에 뜬 표본에서는 critic 의 줄 범위 인용이 plan 사본과 어긋납니다 (절 앵커는 남습니다). 첫 사이클에서 채점자 둘이 독립적으로 이 표류를 Q4 결함으로 잡았습니다. 채점표는 이 경우 절 앵커로 판정하도록 적어 두었지만, 가능하면 critic 직후 (합의표 status 가 아직 open 일 때) 표본을 뜨는 것이 정확합니다.
