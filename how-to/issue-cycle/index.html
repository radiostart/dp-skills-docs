    운영 이슈 단건 처리 (issue 사이클)¶

    한 줄 요약

    팀에 누적된 컨텍스트 (도메인 지식·과거 이슈 이력) 위에서 운영 문제 1건을 진단·수정합니다. 코드 수정이 필요하면 project 와 동일한 planner→critic→generator→evaluator 사이클을 이슈 단위로 사용합니다.

    언제 쓰나¶

    • project 컨텍스트와 무관한 운영 장애·버그·핫픽스·데이터 정합 이슈 1건을 처리할 때
    • 과거 유사 이슈의 원인·조치 기록을 출발점으로 삼고 싶을 때

    활성 project 의 features 에 대한 QA 결함은 /dp-skills:qa 를 사용합니다 — issue 는 project 독립 단건 전용이며 두 스킬은 공존합니다.

    전제¶

    • workspace 가 초기화되어 있을 것 (/dp-skills:team-init).
    • 도메인 컨텍스트 (context/scope/·rules/) 가 채워져 있을수록 진단 품질이 올라갑니다 (/dp-skills:discover).

    절차¶

    1. 이슈 모드 진입¶

    /dp-skills:issue 미사입 일괄 처리에서 환불이 안 되는 문제
반품된 상품이 섞이면 취소가 안 됨

    아는 대로 길게, 여러 줄로 써도 됩니다 — 입력은 폴더명이 아니라 명세의 재료입니다. 길수록 현상 3축이 미리 채워져 사전 인터뷰 질문이 줄어듭니다.

    내부 동작:

    • workspace/{TEAM}/issues/ 에서 유사 이슈를 먼저 검색해 재개/신규를 확인합니다 — 폴더명(영문 slug)과 각 issue.md 의 H1 제목(한글)을 함께 훑으므로 한글 키워드로도 과거 이슈가 걸립니다.
    • 신규면 입력에서 영문 kebab slug 를 뽑아 issues/{slug}/issue.md 를 템플릿으로 생성하고, STATE.md 를 | issue | {slug} | 진행중 | 로 교체합니다. 입력 원문은 버려지지 않습니다 — 첫 줄(또는 핵심 요약)이 H1 제목, 전문이 ## 현상 으로 들어갑니다.
    • 신규 이슈면 사전 인터뷰가 도메인 + 현상 3축 (재현 조건·기대 동작·영향 범위) 을 선택지 질문 1회 (최대 4문항) 로 묶어 묻고, 답변을 issue.md 에 기입한 뒤 해당 scope/·rules/ 를 로드합니다 (상태 파일 없음 — 기록처는 issue.md 자신). 대화에 이미 서술한 축은 질문 없이 채워집니다. 규약 전문: interview.md.

    slug 는 팀 용어의 코드 표기를 우선 채택합니다 — "미사입" 은 rules/retail.md 가 코드 표기를 not_bought 로 명시하므로 not-bought-bulk-refund-fail 이 됩니다. 폴더명으로 소스를 grep 할 수 있게 하려는 것입니다. 입력에 축이 여러 개 섞여 용어 매핑이 갈리면 후보 2~3개를 제시하고 확인을 받습니다.

    인자 없이 /dp-skills:issue (bare) 로 진입하면 폴더·기록이 남지 않고 사이클도 비지원입니다 — 짧은 조사 전용. 진행하던 이슈를 찾으려면 /dp-skills:switch 를 사용하세요.

    2. 현상 확인·보강¶

    신규 이슈는 사전 인터뷰 답변으로 ## 현상 (증상·에러·재현 경로·기대 동작·영향 범위) 이 채워집니다 — "모름" 으로 남긴 축은 (미확인) 으로 표시됩니다. 필요하면 issue.md 를 직접 편집해 보강하고, 선택적으로 ## 의심 영역 을 채웁니다 — AI 탐색 범위와 도메인 후보 제시가 좁아집니다.

    3. 처리 경로 선택¶

    • 조사·경미형 (원인 파악·회신·1줄 수정): 진단 절차대로 직접 처리하고 issue.md 의 ## 원인·## 조치 를 기록합니다.
    • 코드 수정형: 사이클을 시작합니다:
    @ag-planner

    orchestrate-load 가 STATE.md 의 issue 행을 인식해 (work_mode: issue) issues/{이슈명}/ 기반으로 로드하며, 이후 흐름은 project 와 동일합니다:

    단계 산출물 이슈 모드 특칙
    @ag-planner issue.plan[.r{N}].md 최소 변경·롤백 가능, ## 원인 기입, 영향 범위 후보·결함 함수 1줄·회귀 재현 테스트 스텝 필수
    @ag-planner-critic issue.plan.critic[.r{N}].md 챌린지 기준 동일
    @ag-generator 코드 수정 결함 함수 (또는 조치 대상) 범위 내에서만 수정, ## 조치 기입
    @ag-evaluator issue.eval[.r{N}].md 회귀영향 평가 + 회귀 테스트 직접 실행 (test_run skip 금지), ## 조치 기입이 READY 게이트, REPORT 는 phase: issue

    plan 승인·critic blocking·NOT_READY 의 휴먼 게이트는 project 사이클과 동일하게 유지됩니다.

    4. 마무리¶

    • evaluator READY 후 ## 재발 방지 를 기록해 두면 다음 유사 이슈 진단의 출발점이 됩니다.
    • 커밋은 평소처럼 /dp-skills:commit 를 사용합니다. PR 은 gh pr create 로 직접 올립니다 — /dp-skills:pr 는 issue 모드에서 지원하지 않습니다 (아래 주의 참조).
    • 다른 작업으로 전환: /dp-skills:project {프로젝트명} (이슈 폴더·기록은 그대로 남습니다). ## 조치 기입 전에 전환한 미완 이슈는 /dp-skills:switch 목록에 미완 으로 표시되어 다시 찾을 수 있습니다.

    주의¶

    • issue 활성 중 project 전용 스킬은 실행되지 않습니다 — analyze·confl·tdd·create-feature·run-cycle·pr 등은 issue 행을 감지하면 명확히 종료합니다 (preamble P2 mode 판정). pr 은 base 저장뿐 아니라 스킬 전체가 종료됩니다 — projects/{PROJECT}/ state·컨텍스트를 5 지점에서 소비하기 때문입니다. focus 는 예외로 이슈 폴더에 기록됩니다.
    • 기존 이슈 파일은 hook 이 보호합니다 — 재진입 시 Write 덮어쓰기가 차단되고 Edit (원인·조치 기입) 만 허용됩니다.
    • tdd/characterize 모드는 issue 사이클에서 지원하지 않습니다 (standard 고정).
    • Slack 알림은 이슈 모드 미지원입니다 — 활성 행이 issue 면 전송하지 않습니다 (0.33.2 부터 도구가 mode 를 검사해 보장. 종전에는 이슈 slug 와 동명인 프로젝트가 있으면 그 채널로 샐 수 있었습니다).
