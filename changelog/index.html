    변경 이력¶

    사용자에게 영향이 있는 변경만 릴리스 단위로 모았습니다. 전체 커밋 이력은 GitHub Releases 를 참고하세요.

    버전 확인·업그레이드

    현재 설치 버전은 claude plugin list 로 확인합니다. 업그레이드는 claude plugin marketplace update deali-skills 후 claude plugin update dp-skills@deali-skills — 프로젝트 스코프로 설치한 체크아웃은 해당 폴더에서 --scope project 로 따로 갱신해야 합니다. 적용에는 재시작이 필요합니다.

    v0.33.3¶

    • /dp-skills:discover 가 구현을 문서로 옮기지 않습니다 — 산출물에 계산식·조건 분기 순서·반환 키 전수 목록·라인 범위 인용 (파일:100-160) 이 실리는 경우가 있었습니다. 코드가 바뀌면 그 문장은 조용히 오답이 되고, scope 는 모든 phase 에서 로드되므로 토큰 비용도 영구적입니다. 이제 기재 대상이 위치 (경로·심볼) 와 계약·함정 (시그니처·상태값·트랜잭션 경계·암묵 필터·소유권) 으로 고정되고, 구현은 로직 상세는 {파일#메서드} 에서 파악 처럼 위치만 남습니다. 판정 기준은 유용성이 아니라 휘발성입니다 — "다음 릴리즈에 코드가 바뀌면 이 문장이 틀리는가" 가 기준이라, 유용하지만 휘발성이 큰 항목 (계산식이 대표) 은 문서에 두지 않습니다. 소스에 맡긴 영역이 있으면 문서 상단에 기재 범위 고지 1 줄이 붙습니다 (도메인 스코프 추출)
    • 경계 문서의 "호출 계약" 범위가 명확해졌습니다 — 종전 규격은 "인자·반환 시그니처는 유지" 라고만 해서 반환 키 전수 목록까지 계약으로 읽힐 수 있었습니다. 이제 심볼명·인자 형태·반환 형태·실제 분기에 소비되는 키까지가 계약이고, 나머지는 정의 앵커가 대신합니다
    • 도메인 지식 환류 (knowledge-sync) 로 scope 에 직접 문안을 쓸 때도 같은 규격이 적용됩니다 — 미리 보기 승인 게이트를 거치지 않는 경로라 기록 절차에서 한 번 더 확인합니다

    v0.33.2¶

    • 이슈 모드에서 Slack 알림이 다른 프로젝트 채널로 새지 않습니다 — 알림 도구가 STATE.md 의 mode 를 보지 않아, 이슈 이름이 기존 프로젝트 이름과 겹치면 그 프로젝트의 채널 설정으로 메시지가 나갈 수 있었습니다. 이제 활성 행이 issue 면 전송하지 않습니다. 종전에도 대부분은 "폴더가 없어서" 조용히 넘어갔을 뿐 보장은 아니었습니다 (이슈 사이클)
    • /dp-skills:slack 이 보호 상태를 git 기준으로 판정합니다 — 종전 안내문은 ".gitignore 누락 시 자동 주입" 이라고 했지만 실제로는 진단만 하고 있었습니다 (0.23.2 부터 비파괴). 또 doctor 의 .gitignore 검사는 리포 루트만 보는 근사 검사라, 상위 경로 패턴으로 이미 보호된 경우도 경고가 뜹니다. 이제 경고가 떠도 git check-ignore 로 실제 보호 여부를 확인해 진행하고, 정말 보호가 없을 때만 활성화를 멈추고 doctor --fix 를 안내합니다 (status·disable 은 막지 않습니다)
    • /dp-skills:discover 인용 규격이 실사용을 따라잡았습니다 — 산출물과 진단 도구는 이미 심볼 앵커 (파일#메서드) 를 쓰는데 추출 규격 문서만 파일:줄 을 강제하고 있어, 재실행 시 팀이 정착시킨 표기가 되돌아갈 수 있었습니다. 이제 심볼 앵커를 우선하고 (코드가 밀려도 살아남습니다), 심볼로 짚을 수 없는 지점만 줄 번호를 씁니다. 인용을 백틱·괄호로 감싸야 한다는 규칙도 명문화됐습니다 — 감싸지 않으면 drift 검사가 그 파일에서 통째로 꺼집니다 (도메인 스코프 추출)
    • /dp-skills:ai-review 가 엉뚱한 지점에서 분기하지 않습니다 — 현재 브랜치를 그대로 base 로 삼으면서 그것이 대상 PR 의 브랜치인지 확인하지 않았습니다. 이 스킬은 사용자 확인 없이 PR 까지 올리므로 무관한 변경이 실릴 수 있었습니다. 이제 PR 브랜치이거나 앞 차수 fix/... 브랜치면 (의도된 이어붙이기) 그대로 진행하고, 그 외에는 어디서 분기하는지 알리고 확인을 한 번 받습니다
    • 문서와 실제 동작이 어긋나던 곳들을 맞췄습니다 — 이슈 모드에서 /dp-skills:pr 은 실행되지 않는데 매뉴얼은 "평소처럼 사용" 이라고 안내하고 있었습니다 (PR 은 gh pr create 로 직접). tdd 가 없는 경로를 참조 문서로 출력하던 것, dp-doctor 의 검사 범위 목록이 실제 검사의 일부만 담고 있던 것, team-init 이 실제로는 한 파일에만 있는 주석을 "각 파일 상단" 이라고 하던 것도 정정했습니다
    • 재발 방지 — 공통 사전 확인 절차 표에 스킬 행이 빠지면 push 가 막힙니다. 표에서 누락된 스킬은 참조할 행이 없어 자기 문구로 절차를 복제하게 되고, 그게 이번에 발견된 드리프트의 경로였습니다 (code-review-init·discover 2 건)

    v0.33.1¶

    • 스킬 목록 설명 6종이 가벼워졌습니다 (발동 규칙은 그대로) — run-cycle·qa·tdd·create-feature·discover·issue 의 description 에서 운용 상세를 본문으로 위임해, 모든 세션에 상주하는 스킬 목록 컨텍스트를 ~13% 줄였습니다. "명시 호출일 때만 발동" 류 오발동 방지 문구는 원문 그대로 문두에 보존됩니다 — 동작·발동 조건 변화는 없습니다. 재발 방지로 description byte 예산 (스킬당 650B·합계 7,200B) 과 anti-trigger 카나리 게이트가 pre-push 에 추가돼, 이후 스킬 추가·수정 시 예산 초과나 안전 문구 훼손이 push 단계에서 차단됩니다 (핵심 개념 § 스킬 description 계약)

    v0.32.0¶

    • 죽은 README 참조를 기계가 막습니다 — /dp-skills:dp-doctor --schema 가 에이전트·스킬 문서의 README § … 참조를 검사해, 지목한 절이 실제로 없거나 번호(§ 8)로 가리키면 ERROR 를 냅니다. README 는 절 삽입이 잦아 번호가 밀리고, 코드 예시 블록 안의 ## 까지 세면 순번이 어긋납니다 — 검사기는 펜스를 인식해 실제 헤딩만 셉니다. pre-push 에서 자동으로 돕니다
    • ai-review 가 PR 승인을 건너뛰는 이유를 명시했습니다 — /dp-skills:pr 은 PR 생성 전 사용자 확인을 유지되는 게이트로 두는데 /dp-skills:ai-review 는 이를 거치지 않습니다. 명시 호출형 자동화라 호출 자체가 승인이라는 예외를 양쪽 문서에 적었고, 완료 안내에 검증 범위 고지를 추가했습니다 — 적용된 수정은 IDE 진단 확인만 거쳤으므로 검토 책임이 리뷰어에게 있습니다
    • 에이전트 3종의 plan 탐색 규약이 한 곳으로 모였습니다 — 동일한 조사·집계 규칙이 generator·critic·evaluator 에 세 벌로 흩어져 있어 두 릴리스 연속 세 벌을 함께 고쳐야 했습니다. skills/context/shared/plan-target.md 로 추출했습니다 (동작 변화 없음)

    v0.31.2¶

    • 대상 확정 질의는 미완료 plan 이 여럿일 때만 뜹니다 — 0.31.1 에서 넣은 wrapper 대상 확정이, plan 산출물이 삭제되지 않고 쌓이는 탓에 두 번째 feature 이후 매번 발동하고 있었습니다. 평가가 READY 로 끝난 feature 의 plan 을 후보에서 빼서 순차 작업에서는 질의 없이 진행됩니다 (NOT_READY 는 재작업 대상이라 남습니다). 함께 run-cycle 정지 사유의 block 을 wrapper 비정상 종료 로 개명했습니다 — evaluator REPORT 의 status 는 READY | NOT_READY 뿐이라 block 은 나올 수 없는 값이었고, 실제로 잡아야 할 것은 REPORT 없이 끝나는 종료 (orchestrate-load error·plan-validate invalid 등) 였습니다

    v0.31.1¶

    • run-cycle 이 대상 feature 를 지정해 호출합니다 — 큐를 도는 동안 @ag-generator·@ag-evaluator 호출에 feature 번호·plan 경로를 명시합니다 (종전엔 critic 만). 완료 feature 의 plan 이 남아 있을 때 엉뚱한 feature 를 구현·평가하던 무음 오작동이 사라집니다. 평가가 이미 READY 인데 체크박스만 [ ] 인 feature 는 사이클을 다시 돌리지 않고 체크박스만 보정하고, 정지 보고는 사유별 해소 조치를 안내합니다. 세 wrapper 의 대상 탐색은 셸 글롭 대신 Glob 도구를 쓰도록 바꿨습니다 — zsh 는 qa/ 처럼 매칭되지 않는 패턴이 하나만 섞여도 명령 전체를 실행하지 않아 후보가 상시 0 건이었습니다 (미완료 feature 자동 순회)

    • 문서에 "없다" 고 적으려면 근거가 필요합니다 — 전용 서비스 없음·호출처 0 건 류의 부재 주장은 전역 검색으로 반증을 시도한 뒤에만, 시도 범위와 함께 적습니다. 확인이 안 되면 없다 가 아니라 코드에서 확인되지 않음 (범위: …) 입니다. 라우트 전수 조회는 프레임워크 CLI (bin/rails routes 등) 를 1 순위로 쓰고 실행 시점·건수를 함께 남깁니다. 규격이 바뀌어도 기존 scope 는 자동으로 갱신되지 않습니다 — 적용 방법은 도메인 스코프 추출 참고
