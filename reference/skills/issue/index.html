    /dp-skills:issue¶

    운영 이슈 처리 모드 활성화 — workspace/{TEAM}/issues/{이슈명}/ 를 생성·로드하고 팀 누적 컨텍스트 위에서 문제 1건을 해결한다. 코드 수정 시 project 와 동일한 planner→critic→generator→evaluator 사이클을 issue 단위로 사용 가능. 버그 대응·장애 분석·핫픽스 등 단발성 작업용. 지속적인 기능 개발·feature 단위 작업은 /dp-skills:project 를 사용한다.

    운영 이슈 처리 모드를 활성화한다.

    정의 — issue 는 기존에 누적된 컨텍스트를 기반으로 특정 문제를 해결하는 단건 처리 기능이다:

    1. 누적 컨텍스트 기반: projects/ 산출물과는 독립 — "프로젝트 컨텍스트 미참조" 는 projects/ 산출물 (project.md·features/·agents/) 한정이며, 팀 누적 컨텍스트 (context/ 도메인 지식·과거 issues/ 이력·메모리 P0) 는 진단의 기반이다.
    2. project 유사 구조의 단건 처리: 이슈 폴더는 issue.md 1 건의 명세 + 사이클 파생 산출물로 구성된다 — feature N 건 대신 문제 1 건. 파생 산출물 명명은 GUIDE.md § 이슈 폴더 구조 (qa 산출물 명명 규약 준용) 를 따른다.
    3. 기본 사이클 유지: 코드 수정이 필요한 이슈는 @ag-planner → @ag-planner-critic → @ag-generator → @ag-evaluator 사이클을 그대로 사용한다 (orchestrate-load 가 STATE.md 의 issue 행을 인식해 issues/ 기반으로 로드 — work_mode 계약). 조사·회신만으로 끝나는 이슈는 사이클 없이 직접 처리해도 된다.

    QA 결함 처리는 /dp-skills:qa 를 사용하세요. issue 는 project 컨텍스트 독립 운영 장애 전용입니다.

    대상 이슈: $ARGUMENTS

    사전 확인¶

    preamble.md 의 P-1, P0, P1 수행.

    • P-1: 진행 보드 선로딩 (다단계 스킬).
    • P0: 컨텍스트의 MEMORY.md 인덱스에서 인자의 이슈명·키워드와 관련된 메모를 가려 본문을 Read 하여 유사 이슈 이력 반영.
    • P1: 팀 이름 {TEAM} 획득.

    수행 절차¶

    1. bare 진입 — $ARGUMENTS 가 비어있으면: "이슈명 없이 진입합니다 — 폴더·기록이 남지 않고 사이클 (@ag-*) 도 비지원입니다. 기록과 사이클이 필요하면 /dp-skills:issue {이슈명} 으로 재진입하세요." 1 줄 고지 후 GUIDE.md 를 로드하고, 2·3 단계를 건너뛰어 4 단계부터 진행한다 (5 단계는 MANIFEST 까지만, 6 단계 안내에서 사이클 항목 제외).
    2. 유사 이슈 검색 — 폴더명과 제목을 함께 훑어 유사 이슈를 찾는다 (과거 원인·조치가 이번 진단의 출발점). 폴더명은 영문 slug 라 한글 키워드는 제목이 받는다:
    ls workspace/{TEAM}/issues/ 2>/dev/null
grep -H "^# " workspace/{TEAM}/issues/*/issue.md 2>/dev/null
    • 유사 폴더 발견 → 사용자에게 제시: "유사 이슈가 있습니다: {목록}. 해당 이슈를 재개할까요, 새 이슈로 진행할까요?" (목록은 {slug} — {제목} 형식)
    • H1 제목이 없는 기존 이슈는 폴더명으로만 매칭한다 — 소급 기입하지 않는다.
    • 없으면 다음 단계로.
    • 이슈 slug 결정 + 폴더 생성/로드 — 폴더명 (= 이슈명) 은 $ARGUMENTS 원문이 아니라 원문에서 도출한 영문 kebab slug 다. 원문은 버리지 않는다 — 제목·현상으로 보존한다 (GUIDE.md § 이슈 폴더 구조 가 명명 SSOT).
    • slug 도출 — 원문의 핵심 키워드를 소문자 영문 kebab-case 로 축약한다 ([a-z0-9-] 만, 40 자 이내). 팀 용어는 임의 번역하지 말고 context/rules/·enums/ 의 코드 표기를 우선 채택한다 (예: "미사입" → rules/retail.md 가 코드 표기를 not_bought 로 명시 → not-bought) — 폴더명으로 소스를 grep 할 수 있게 하려는 것이다.
    • 후보 제시 — 원문에 축이 둘 이상 섞여 있거나 (용어 불일치·복수 증상) 용어 매핑이 모호하면 후보 2~3 개를 제시하고 사용자 확정을 받는다. 명확하면 확인 없이 진행하되 결정한 slug 를 1 줄 고지한다.
    • 없으면: GUIDE.md 를 로드하여 issues/{slug}/issue.md 를 템플릿대로 생성한다 — H1 = 원문 1 줄 요약 (여러 줄 입력이면 첫 줄 또는 핵심 요약 1 줄, 개행·| 제거), ## 현상 = 원문 전문, 도메인: 라인 포함 (값은 5 단계에서 확정).
    • 있으면: issue.md 만 Read 한다 (GUIDE.md 는 로드하지 않는다). slug 를 재도출하지 않는다. 파생 산출물 (issue.plan*.md·issue.eval*.md) 이 있으면 진행 상태를 요약한다 (6 단계 재개 분기의 근거).
    • preamble.md 의 P3 수행 — STATE.md 테이블 본문을 | issue | {이슈명} | 진행중 | 1행으로 교체. 기록 값은 3 단계에서 확정한 slug 다 (원문·제목 아님 — 표는 1 행 규약이라 개행·| 가 섞이면 행 파서가 깨진다). 기존 다른 이름 행은 모두 삭제 (이력의 SSOT 는 issues/ 로컬 폴더). 이슈명이 없으면 (bare) | issue | - | 진행중 | 로 기록한다.
    • 도메인 확정 + 컨텍스트 로드 — preamble.md 의 P4 수행 (issue 분기 — 도메인 소스가 issue.md 의 도메인: 라인이라는 계약과 wrapper 일치 사유는 P4 가 SSOT).
    • 신규 생성 경로 (절차 3 에서 issue.md 를 방금 생성) 는 5-bis 사전 인터뷰가 도메인 질의를 흡수한다 — 인터뷰 발동 시 본 항의 자유 질의는 수행하지 않는다 (P4 "1 회 질의" 계약의 이행 수단만 교체, 재질의 없음).
    • 그 외 경로에서 도메인: 라인 부재 시 1 회 질의: ## 의심 영역 내용과 context/scope/ 트리를 대조해 후보를 제시하고 사용자 확정을 받은 뒤, issue.md 상단에 도메인: {값} 1 줄을 Edit 으로 기입하고 scope/rules 를 로드한다. 판단이 어려우면 미정으로 진행 가능 (MANIFEST 까지만 — wrapper 진입 시 재질의된다).
    • bare 모드는 질의 없이 MANIFEST 까지만.

    5-bis. 사전 인터뷰 (조건부 — 신규 생성 경로 한정). 공통 규약 (질의 상한·탈출구·갭 앵커·JIT 로드·미해소 처리): interview.md. - 발동 판정 — 현상 3축 (재현 조건 · 기대 동작 · 영향 범위) 중 $ARGUMENTS·대화 맥락에서 채울 수 없는 축이 있으면 발동. 판정 대상은 $ARGUMENTS 전문이다 (여러 줄 입력이면 모든 줄). 이미 서술된 축은 해당 bullet 에 채우고, 전부 채워지면 질의 없이 통과 — 원문을 길게 쓸수록 질문이 줄어든다. 짧은 한 줄 진입에서는 사실상 항상 발동하는데, 이는 신규 마찰이 아니라 기존 "사용자가 issue.md 를 직접 채우는" 현상 작성 단계의 구조화 대체다. - 질문 생성 전 그 시점 가용 컨텍스트 (P0 유사 이슈 메모 · context/scope/ 트리 · MANIFEST) 를 대조한다 — 답이 있는 것은 질문 금지 (지식 우선). - 발동 시 ToolSearch select:AskUserQuestion 선로딩 후 1 회 질의 (최대 4 문항). 우선순위: 도메인 (라인 부재 시 — 절차 5 질의 흡수) > 현상 3축 > (d)-성 발견분 (interview.md § 갭 앵커 규칙으로 선기록). - 답변은 issue.md 에 Edit 반영 — 현상 bullet·도메인: 라인 (도메인 확정 시 scope/rules 로드는 절차 5 본류와 동일). 도메인 "모름" 답변 → 미정 진행 (P4 허용 — 재질의 없음). 미해소 축은 해당 bullet (미확인) 잔존. - (d)-성 미해소는 ## Open Questions 를 4 카테고리 H3 형식으로 신설해 - [ ] 기입 (GUIDE.md § 섹션 구조 — H3 없는 bare 항목은 기계 검증에 계수되지 않는다). - 비발동: bare 모드 (기록처 없음) · 기존 이슈 재로드. - A2 runtime fallback: 질의 실패·도구 로드 실패 시 → 진행 (abort 안 함). 빈 축은 사용자가 직접 기입하는 기존 흐름으로 폴백. 6. 결과 출력 — 이슈 컨텍스트를 요약하고 다음 작업을 안내한다. 산출물 상태로 분기한다 (명시적 if / elif / else — 한 번에 하나의 안내만): 1. issue.eval*.md 의 최신 REPORT 가 READY 면: "이슈 조치가 완료된 상태입니다. ## 재발 방지 기록 여부를 확인하세요." 안내. 2. elif issue.plan*.md 존재: "작성된 plan 이 있습니다 — 재개: 챌린지 전이면 @ag-planner-critic, plan 승인 후면 @ag-generator." 안내 (승인 흔적은 산출물에 없으므로 기존 plan 재개 시 사용자 재확인). 3. else: 처리 경로를 분기해 안내한다: - 코드 수정형 (원인이 코드 결함으로 추정): "@ag-planner 를 호출해 사이클을 시작하세요 — plan 은 issues/{이슈명}/issue.plan.md 에 저장되고, critic 챌린지 → generator 구현 → evaluator 검증 (회귀 재현 테스트 실행 포함) 이 이어집니다." - 조사·경미형 (원인 파악·회신·데이터 확인 중심): "GUIDE 의 진단 절차대로 직접 처리할 수 있습니다. 처리 후 issue.md 의 ## 원인·## 조치 를 기록하세요."
