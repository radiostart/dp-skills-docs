    /dp-skills:run-cycle¶

    활성 project 의 미완료 feature 들을 순서대로 자동 순회하며 planner→critic→generator→evaluator 사이클을 진행하는 순차 오토파일럿 (human-on-the-loop). green 신호에는 사전 승인 없이 자동 진행하고 Slack progress 로 사후 통지하며, critic blocking·NOT_READY 재시도 소진·block· wrapper 질의 등 red 에서만 정지한다 (판정 상세·정지 전수 목록은 본문 §2.3·§3). 종전 사전 승인 흐름은 --gated 로 회귀. 큐는 project.md 의 [ ] 미완료 feature 에서 파생하며 별도 상태 파일을 쓰지 않는다 (stateless, 재실행=재개). 병렬 아님 — 한 번에 1 feature. 수동 @mention 사이클은 불변.

    메인 루프에서 @ag-planner·@ag-planner-critic·@ag-generator·@ag-evaluator 를 순서대로 호출한다 (subagent 가 subagent 를 띄우지 않음). 사전 결재 대신 검증 산출물 (critic 합의표·evaluator REPORT) 이 게이트다.

    대상: $ARGUMENTS (옵션: feature 부분집합 #3-5 · #3 #4 · --gated — 종전 human-in-the-loop 게이트 (plan 사전 승인·재개 재승인) 전부 복원. per-invocation 플래그다 — 상태 파일에 저장되지 않으므로 (stateless) 정지 후 재실행 시 재지정한다.)

    사전 확인¶

    preamble.md P-1(TodoWrite 선로딩) · P1(팀) · P2(활성 project) 수행. 활성 project 없으면 P2 메시지로 종료. .agent-state.yml 의 phase 가 qa 면 "run-cycle 은 development phase 전용" 안내 후 종료.

    1. 큐 구성 (project.md 파생)¶

    1. 활성 project 의 project.md ## 목표 에서 [ ] 미완료 feature 를 목록 순서대로 수집 ([x] 제외). 의존성 메타데이터가 없으므로 순서를 재계산하지 않고 목록 순서를 신뢰한다.
    2. 인자로 #3-5·#3 #4 명시 시 그 부분집합으로 필터.
    3. 큐가 비면 → "신규 작업 없음 (모든 목표 완료)" 출력 후 종료.
    4. 큐를 표시하고 확인 없이 즉시 시작한다 — 스킬 호출 자체가 진행 의도다. 시작 시 Slack 통지 1회:
    python3 ${CLAUDE_PLUGIN_ROOT}/tools/slack-notify.py --event progress \
  --workspace workspace --message "run-cycle 시작: {큐 요약 (#3 → #4 → #5)}"

    (.slack.env 부재 시 자동 no-op — 호출은 그대로 실행. 이하 모든 progress 동일.)

    2. feature 1건 사이클 루프¶

    큐의 각 feature 를 순서대로 처리한다.

    2.1 재개 지점 판정 (stateless) — 항상 선행¶

    feature 산출물로 "가장 이른 미완료 단계" 를 정한다. 이 판정이 게이트 검사보다 먼저다 — 게이트 통과가 재개 지점을 앞당기지 않는다 (구현 완료 상태에서 generator 를 재실행해 같은 feature 를 이중 적용하는 경로 봉쇄):

    • features/NN-{slug}.plan.md 없음 → planner 부터 (§2.2)
    • 유효한 .plan.md 있음 (tools/plan-validate.py 통과) + .eval.md 없음 → 재개 지점을 먼저 정한다:
    • plan 스텝에 미완료 진행 흔적이 있거나 판단이 애매하면 → 재개 지점 = critic/generator
    • plan 전 스텝 완료 ([x]·[Green] 증거) + 구현이 끝난 상태 → 재개 지점 = evaluator (§2.5)

    그 다음 재개 게이트 를 통과시킨다 (승인 사실은 산출물에 없으므로 합의표가 증거): - .plan.critic.md 존재 + critic-lint 통과 + blocking 미해결 (open/deferred) 0 → 재승인 없이 판정된 재개 지점부터 진행 + progress 통지 ("재개: #{N} {지점}"). - .plan.critic.md 없음 → critic 호출로 합의표 확보 (§2.3) 후, blocking 0 이면 판정된 재개 지점부터 (critic green 이 generator 를 강제하지 않는다 — 구현 완료 상태면 evaluator 로). blocking ≥ 1 → §3 정지. - blocking deferred·open 잔존 → §3 정지 (§2.3 판정 준용). - --gated: 합의표 유무와 무관하게 plan 을 사용자에게 재제시하고 승인 후 재개 (종전 동작). - features/NN-{slug}.eval.md 가 NOT_READY → generator 재작업부터 (§2.4→§2.5). 이 경로의 재작업도 §2.5 의 재시도 1회에 계상한다 (세션 기준).

    완료([x]) feature 는 큐에 없으므로 도달하지 않는다.

    2.2 planner¶

    @ag-planner 호출 → .plan.md 산출. 호출 프롬프트에 feature 번호·slug 와 [orchestration: hotl] 마커를 포함한다 — planner 가 절차 4 의 승인 대기를 "계획 확정 보고" 로, 절차 7 의 approval Slack 통지를 생략 (통지는 본 스킬의 progress 로 일원화 — 채널에 "⏸ 승인 필요" 거짓 신호 방지) 로 전환한다.

    • 기본 (HOTL): plan 산출·plan-validate 통과 후 사용자 승인 대기 없이 §2.3 (critic) 으로 즉시 진행. plan 은 산출물로 남아 사후 감사 대상.
    • --gated: 마커를 넣지 않고 호출하며, 산출된 plan 을 사용자에게 제시하고 승인을 기다린다 (종전 ⏸ plan 승인 게이트). 미승인·거부 → §3 정지.

    2.3 critic — 자동 진행의 판정자¶

    @ag-planner-critic 호출 (HOTL 필수 — 스킵 없음) → .plan.critic.md 산출. 호출 프롬프트에 feature 번호·slug·대상 plan 경로를 명시한다 — 큐 진행 중엔 완료 feature 의 plan 이 잔존해 critic 절차 2 의 후보 탐색이 복수를 만나므로, 명시 없이는 critic 이 후보 선택 질의로 정지한다.

    판정 절차:

    1. [필수 선행] critic-lint — 합의표 무결성을 결정론 검증한다:
    python3 ${CLAUDE_PLUGIN_ROOT}/tools/critic-lint.py \
  workspace/{TEAM}/projects/{PROJECT}/features/NN-{slug}.plan.critic.md

    exit 1 (본문 챌린지 ↔ 표 불일치·행 누락·enum 위반) → §3 정지 (합의표 불일치). 행 누락 산출물로 blocking 0 을 판독하는 거짓 통과 경로를 봉쇄한다.

    1. 합의 표 판독 (열: severity·status. critic 이 행마다 severity + status=open 으로 emit — ag-planner-critic 절차 5):
    2. blocking 미해결 행 (severity=blocking 이고 status ∈ {open, deferred}) 이 1개라도 있으면 → §3 정지 ("blocking 미해소 시 generator 진행 금지". deferred=이월 도 미해결 — accepted·rejected 만 처리 완료).

    3. blocking 0 (또는 전부 accepted·rejected) → 합의 표를 수정하지 않고 자동 진행 + progress 통지:

      python3 ${CLAUDE_PLUGIN_ROOT}/tools/slack-notify.py --event progress \
  --workspace workspace \
  --message "feature #{N} {slug} plan green (blocking 0·suggestion {M}·nit {K}) — 진행"

      suggestion·nit 은 status 무관 비정지. 합의 표는 critic·planner 소유 — run-cycle 은 읽기만 한다 (status 전이는 planner 절차 10 만 수행).

    2.4 generator¶

    @ag-generator 호출 → 구현.

    2.5 evaluator¶

    @ag-evaluator 호출 → VERIFICATION REPORT.

    • READY → project.md 해당 feature 체크박스 [x] 갱신. REPORT 의 metrics.domain_impact 가 detected 면 항목을 메모리에 누적하고 (질의·정지 없음 — green 자동 진행 유지) → 자동 다음 feature(2.1 로).
    • NOT_READY → bounded retry (feature 당 1회, 본 세션 한정):
    • issues_to_fix 에 "planner 재호출 필요" 류 plan-level 반려가 있으면 재시도 없이 즉시 §3 정지 — generator 재작업으로 못 고치는 구조적 실패라 자동 라운드가 낭비다.
    • 그 외 (구현 결함) → issues_to_fix 를 generator 재작업 프롬프트에 전달해 §2.4→§2.5 를 1회만 자동 재수행 + progress 통지 ("feature #{N} NOT_READY — 재작업 1회차"). 재평가도 NOT_READY 면 → §3 정지 (재시도 소진).
    • 재시도 카운트는 본 세션 컨텍스트로만 유지한다 (상태 파일 금지). 세션이 끊기고 재실행되면 리셋된다 — per-session bound 로 의도된 동작.
    • block → §3 정지.

    3. 정지 정책¶

    정지 사유 (HOTL): critic blocking 미해소 · 합의표 불일치 (critic-lint FAIL) · NOT_READY 재시도 소진 · plan-level 반려 · block · wrapper 의 사용자 질의 대기 (OQ 게이트·모드 가드·도메인 복수 후보 등 — wrapper 유지 게이트가 발동한 경우) · (--gated 한정) plan 미승인. 도달 시:

    • 큐 전체 정지. 뒤 feature 로 진행하지 않는다 — N+1 이 N 에 의존할 수 있고 의존성 데이터가 없어 알 길이 없다.
    • 정지 사유·해당 산출물 (REPORT·합의표·critic-lint 출력) 과 게이트 이력 표 (§4 와 동일 형식 — 정지 시점까지 처리분) 를 출력한다.
    • Slack approval 통지 1회: --event approval --message "run-cycle 정지: #{N} {사유}" — 개입 요청은 approval, 자동 진행은 progress 로 채널에서 구분된다.
    • 안내: /dp-skills:fix-review 로 처리 → 수정 후 /dp-skills:run-cycle 재실행(=재개). 부분집합·--gated 로 돌렸다면 같은 인자를 다시 넘긴다.
    • 누적된 domain_impact 항목이 있으면 정지 보고에 "도메인 지식 환류 제안 (누적)" 표를 함께 출력한다 — 처리 여부는 사용자 결정 (knowledge-sync.md § run-cycle).

    4. 큐 완료¶

    모든 feature READY → 완료 요약 + 게이트 이력 표 (사후 감사 뷰) 출력:

    | feature | critic (blocking/suggestion/nit) | retry | verdict |
| ------- | -------------------------------- | ----- | ------- |
| #3 slug | 0 / 2 / 1                        | 0     | READY   |
| #4 slug | 0 / 0 / 0                        | 1     | READY   |

    누적된 domain_impact 항목이 있으면 "도메인 지식 환류 제안 (누적)" 표를 출력하고 기록 여부를 질의한다. 승인 시 knowledge-sync.md § 기록 을 수행한다 (항목 5건 이상이면 /dp-skills:discover 재실행 권장).

    Do-NOT¶

    • feature 병렬 진행 금지 — 한 번에 1 feature (.focus.md·STATE.md 싱글톤· generator 파일 충돌 회피).
    • 무검증 자동 통과 금지 — critic-lint 통과 + 합의표 blocking 0 없이 generator 진행 금지. critic 스킵 금지 (HOTL 에서 critic 은 필수 판정자다). NOT_READY· block 자동 통과 금지.
    • NOT_READY 재시도 1회 초과 금지 — 재실패는 정지 (수렴 루프 금지).
    • 재개 게이트 통과가 재개 지점을 앞당기는 것 금지 — §2.1 판정 지점이 우선 (구현 완료 feature 의 generator 재실행 = 이중 적용).
    • --gated 시 종전 게이트 전부 복원 — plan 사전 승인·재개 재승인을 생략하지 않는다 ([orchestration: hotl] 마커도 넣지 않는다).
    • 정지 후 뒤 feature 자동 진행 금지.
    • 상태 파일 생성 금지 — 큐·진행·재시도 카운트는 project.md + 산출물 + 세션 컨텍스트에서 파생.
    • 수동 사이클·@ag-* 동작 변경 금지 — 본 스킬은 호출 순서와 오케스트레이션 마커만 관리한다.
    • feature 마다 domain_impact 질의로 정지 금지 — 누적 후 큐 종료 시 일괄 질의.
