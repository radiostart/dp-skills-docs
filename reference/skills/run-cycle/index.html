    /dp-skills:run-cycle¶

    사용자가 자동 순회를 명시 요청했을 때만 사용한다 (/dp-skills:run-cycle 또는 상당 지시) — "계속·이어서 진행해줘" 류 발화만으로 자발 발동하지 않는다 (필요해 보이면 큐 제시 후 확인 1회). 활성 project 의 미완료 feature 를 에이전트 사이클 (planner→critic→generator→evaluator) 로 자동 순회하는 순차 오토파일럿 (HOTL) — 한 번에 1 feature, 수동 @mention 사이클 불변. green 진행/red 정지 판정·--gated·큐 규칙은 본문이 정의한다.

    메인 루프에서 @ag-planner·@ag-planner-critic·@ag-generator·@ag-evaluator 를 순서대로 호출한다 (subagent 가 subagent 를 띄우지 않음). wrapper 호출은 동기 실행이다 — 직전 단계 산출물을 수신·판독하기 전에 다음 단계를 기동하지 않는다 (background·병행 기동 금지 — 하니스가 background 를 기본으로 제공해도 사용하지 않는다). 사전 결재 대신 검증 산출물 (critic 합의표·evaluator REPORT) 이 게이트다.

    대상: $ARGUMENTS (옵션: feature 부분집합 #3-5 · #3 #4 · --gated — 종전 human-in-the-loop 게이트 (plan 사전 승인·재개 재승인) 전부 복원. per-invocation 플래그다 — 상태 파일에 저장되지 않으므로 (stateless) 정지 후 재실행 시 재지정한다.)

    사전 확인¶

    preamble.md P-1(진행 보드 선로딩) · P1(팀) · P2(활성 project) 수행. 활성 project 없으면 P2 메시지로 종료. .agent-state.yml 의 phase 가 qa 면 "run-cycle 은 development phase 전용" 안내 후 종료.

    1. 큐 구성 (project.md 파생)¶

    1. 활성 project 의 project.md ## 목표 에서 [ ] 미완료 feature 를 목록 순서대로 수집 ([x] 제외). 의존성 메타데이터가 없으므로 순서를 재계산하지 않고 목록 순서를 신뢰한다.
    2. 인자로 #3-5·#3 #4 명시 시 그 부분집합으로 필터.
    3. 큐가 비면 → "신규 작업 없음 (모든 목표 완료)" 출력 후 종료.
    4. 큐를 표시하고 확인 없이 즉시 시작한다 — 본 스킬은 사용자 명시 호출 전용 (description 발동 조건) 이므로 스킬 호출 자체가 진행 의도다. 시작 시 Slack 통지 1회:
    python3 ${CLAUDE_PLUGIN_ROOT}/tools/slack-notify.py --event progress \
  --workspace workspace --message "run-cycle 시작: {큐 요약 (#3 → #4 → #5)}"

    (.slack.env 부재 시 자동 no-op — 호출은 그대로 실행. 이하 모든 progress 동일.)

    2. feature 1건 사이클 루프¶

    큐의 각 feature 를 순서대로 처리한다.

    2.1 재개 지점 판정 (stateless) — 항상 선행¶

    feature 산출물로 "가장 이른 미완료 단계" 를 정한다. 이 판정이 게이트 검사보다 먼저다 — 게이트 통과가 재개 지점을 앞당기지 않는다 (구현 완료 상태에서 generator 를 재실행해 같은 feature 를 이중 적용하는 경로 봉쇄).

    아래 분기를 위에서부터 순서대로 검사하고 처음 매칭된 하나만 적용한다. 조건이 동시에 성립하는 입력이 있으므로 (예: .plan.md 만 지워진 READY feature) 순서 자체가 판정의 일부다 — .eval.md 판정을 앞에 두는 이유는 그것이 사이클의 최종 산출물이기 때문이다 (뒤 단계의 증거가 앞 단계의 부재를 이긴다):

    1. .eval.md 의 status 가 READY — status: 값이 정확히 READY 인 경우만 해당한다. NOT_READY 는 2 번 분기다 (부분 문자열 매칭으로 삼키지 않는다 — READY 는 NOT_READY 에 포함된다). 큐에 있다는 건 project.md 체크박스가 [ ] 라는 뜻이다 → 사이클을 재실행하지 않는다. [x] 갱신만 수행하고 §2.5 의 READY 후처리 (domain_impact 누적·게이트 이력 1줄) 를 거쳐 다음 feature 로 넘어간다. 평가는 이미 통과했으므로 어느 단계든 재실행은 이중 적용이다. 이번 큐에서 사이클을 돌지 않았으므로 이력 1줄의 critic·retry 는 둘 다 - 로 적고 (지어내지 않는다) 끝에 (체크박스 보정) 을 덧붙인다. 이 상태는 evaluator step 5 의 Edit 실패·§2.5 갱신 직전 세션 중단·사용자의 수동 [ ] 되돌림으로 생긴다 — 되돌림이 재작업 의도였다면 .eval.md 를 지운 뒤 재실행한다. 본 분기는 산출물만 보고 판정하며 .focus.md 는 읽지 않는다 (focus 로 재작업을 지시해도 이 분기를 되돌리지 못한다).
    2. .eval.md 의 status 가 NOT_READY → generator 재작업부터 (§2.4→§2.5). 이 경로의 재작업도 §2.5 의 재시도 1회에 계상한다 (세션 기준).
    3. features/NN-{slug}.plan.md 없음 → planner 부터 (§2.2). plan 이 있으나 plan-validate 가 실패하는 (invalid) 경우도 본 분기로 취급한다 — 보완 주체가 planner 이므로 §2.2 부터다.

    4. 유효한 .plan.md 있음 (tools/plan-validate.py 통과) + .eval.md 없음 → 재개 지점을 먼저 정한다:

    5. plan 스텝에 미완료 진행 흔적이 있거나 판단이 애매하면 → 재개 지점 = critic/generator

    6. plan 전 스텝 완료 ([x]·[Green] 증거) + 구현이 끝난 상태 → 재개 지점 = evaluator (§2.5)

    그 다음 재개 게이트 를 통과시킨다 (승인 사실은 산출물에 없으므로 합의표가 증거):

    • .plan.critic.md 존재 + critic-lint 통과 + blocking 미해결 (open/deferred) 0 → 재승인 없이 판정된 재개 지점부터 진행 + progress 통지 ("재개: #{N} {지점}").
    • .plan.critic.md 없음 → critic 호출로 합의표 확보 (§2.3) 후, blocking 0 이면 판정된 재개 지점부터 (critic green 이 generator 를 강제하지 않는다 — 구현 완료 상태면 evaluator 로). blocking ≥ 1 → §3 정지.
    • blocking deferred·open 잔존 → §3 정지 (§2.3 판정 준용).
    • --gated: 합의표 유무와 무관하게 plan 을 사용자에게 재제시하고 승인 후 재개 (종전 동작).

    완료([x]) feature 는 큐에 없으므로 도달하지 않는다 — 단 [x] 부재가 미완료를 보장하지는 않으므로 (분기 1) 큐 소속만으로 사이클 재실행을 결정하지 않는다.

    2.2 planner¶

    @ag-planner 호출 → .plan.md 산출. 호출 프롬프트에 feature 번호·slug 와 [orchestration: hotl] 마커를 포함한다 — planner 가 절차 4 의 승인 대기를 "계획 확정 보고" 로, 절차 7 의 approval Slack 통지를 생략 (통지는 본 스킬의 progress 로 일원화 — 채널에 "⏸ 승인 필요" 거짓 신호 방지) 로 전환한다.

    • 기본 (HOTL): plan 산출·plan-validate 통과 후 사용자 승인 대기 없이 §2.3 (critic) 으로 즉시 진행. plan 은 산출물로 남아 사후 감사 대상.
    • --gated: 마커를 넣지 않고 호출하며, 산출된 plan 을 사용자에게 제시하고 승인을 기다린다 (종전 ⏸ plan 승인 게이트). 미승인·거부 → §3 정지.

    2.3 critic — 자동 진행의 판정자¶

    @ag-planner-critic 호출 (HOTL 필수 — 스킵 없음) → .plan.critic.md 산출. 호출 프롬프트에 feature 번호·slug·대상 plan 경로를 명시한다 — 큐 진행 중엔 완료 feature 의 plan 이 잔존해 critic 절차 2 의 후보 탐색이 복수를 만나므로, 명시 없이는 critic 이 후보 선택 질의로 정지한다.

    판정 절차:

    1. [필수 선행] critic-lint — 합의표 무결성을 결정론 검증한다:
    python3 ${CLAUDE_PLUGIN_ROOT}/tools/critic-lint.py \
  workspace/{TEAM}/projects/{PROJECT}/features/NN-{slug}.plan.critic.md

    exit 1 (본문 챌린지 ↔ 표 불일치·행 누락·enum 위반) → §3 정지 (합의표 불일치). 행 누락 산출물로 blocking 0 을 판독하는 거짓 통과 경로를 봉쇄한다.

    1. 합의 표 판독 (열: severity·status. critic 이 행마다 severity + status=open 으로 emit — ag-planner-critic 절차 5):
    2. blocking 미해결 행 (severity=blocking 이고 status ∈ {open, deferred}) 이 1개라도 있으면 → §3 정지 ("blocking 미해소 시 generator 진행 금지". deferred=이월 도 미해결 — accepted·rejected 만 처리 완료).

    3. blocking 0 (또는 전부 accepted·rejected) → 합의 표를 수정하지 않고 자동 진행 + progress 통지:

      python3 ${CLAUDE_PLUGIN_ROOT}/tools/slack-notify.py --event progress \
  --workspace workspace \
  --message "feature #{N} {slug} plan green (blocking 0·suggestion {M}·nit {K}) — 진행"

      suggestion·nit 은 status 무관 비정지. 합의 표는 critic·planner 소유 — run-cycle 은 읽기만 한다 (status 전이는 planner 절차 10 만 수행).

    2.4 generator¶

    @ag-generator 호출 → 구현. 호출 프롬프트에 feature 번호·slug·대상 plan 경로를 명시한다 (§2.3 과 동일 사유 — 큐 진행 중엔 완료 feature 의 plan 이 잔존한다). generator 는 후보가 복수면 선택 질의로 정지하지만 후보가 1 개면 질의 없이 채택하므로 (ag-generator step 2), 잔존 plan 이 1 개뿐인 상태에서 미명시는 그대로 무음 오작동이 된다.

    2.5 evaluator¶

    @ag-evaluator 호출 → VERIFICATION REPORT. generator 와 동일하게 feature 번호·slug·대상 plan 경로를 명시한다 — 미명시는 다른 feature 를 평가하고 그 .eval.md 를 덮어쓰는 경로다.

    • READY → project.md 해당 feature 체크박스가 [ ] 로 남아 있으면 [x] 로 보정 갱신 (primary writer 는 evaluator step 5 — 정상 경로에서는 이미 [x] 다. 미체크로 남는 사유는 §2.1 분기 1 참조). REPORT 의 metrics.domain_impact 가 detected 면 항목을 메모리에 누적하고 (질의·정지 없음 — green 자동 진행 유지) → 게이트 이력 1줄을 사용자 대면 텍스트로 출력 후 자동 다음 feature(2.1 로):
    #N {slug}: critic {b}/{s}/{n} · retry {r} · READY · 인자 {부분집합·--gated 또는 "없음"}

    긴 큐에서 컨텍스트가 요약돼도 재시도 카운트·호출 인자가 대화에 앵커로 남아 재시도 상한 (1회)·인자 유지가 복원된다 (상태 파일 아님 — Do-NOT 정합). - NOT_READY → bounded retry (feature 당 1회, 본 세션 한정): - issues_to_fix 에 "planner 재호출 필요" 류 plan-level 반려가 있으면 재시도 없이 즉시 §3 정지 — generator 재작업으로 못 고치는 구조적 실패라 자동 라운드가 낭비다. - 그 외 (구현 결함) → issues_to_fix 를 generator 재작업 프롬프트에 전달해 §2.4→§2.5 를 1회만 자동 재수행 + progress 통지 ("feature #{N} NOT_READY — 재작업 1회차"). 재평가도 NOT_READY 면 → §3 정지 (재시도 소진). - 재시도 카운트는 본 세션 컨텍스트로만 유지한다 (상태 파일 금지). 세션이 끊기고 재실행되면 리셋된다 — per-session bound 로 의도된 동작. - wrapper 비정상 종료 (REPORT 없이 끝남 — orchestrate-load error·plan-validate invalid·모드 게이트 중단 등) → §3 정지. REPORT 의 status 는 READY | NOT_READY 둘뿐이므로 (verify-report-lint.py 의 VALID_STATUS 가 강제) 제 3 의 판정값을 기다리지 않는다 — 산출물이 없는 종료가 곧 이 사유다. (block 은 @ag-code-reviewer 의 verdict 어휘이며 사이클 안에서는 쓰이지 않는다.)

    3. 정지 정책¶

    정지 사유 (HOTL): critic blocking 미해소 · 합의표 불일치 (critic-lint FAIL) · NOT_READY 재시도 소진 · plan-level 반려 · wrapper 비정상 종료 · wrapper 의 사용자 질의 대기 (OQ 게이트·모드 가드·도메인 복수 후보 등 — wrapper 유지 게이트가 발동한 경우) · (--gated 한정) plan 미승인. 도달 시:

    • 큐 전체 정지. 뒤 feature 로 진행하지 않는다 — N+1 이 N 에 의존할 수 있고 의존성 데이터가 없어 알 길이 없다. 본 정지는 사용자만 해소할 수 있는 입력 대기다 — "완료까지 계속" 류 자율 진행 지침의 예외에 해당하며, 정지 사유를 모델이 자체 해소·우회해 재개하지 않는다.
    • Slack approval 통지 1회: --event approval --message "run-cycle 정지: #{N} {사유}" — 개입 요청은 approval, 자동 진행은 progress 로 채널에서 구분된다.

    • 정지 보고 — 아래 순서로 출력하며 "다음 행동" 블록이 항상 마지막이다. 블록 뒤에 참고·부수 문단을 덧붙이지 않는다 — 사용자가 마지막에 읽는 것이 행동이어야 한다.

    • 정지 사유 · 해당 산출물 (REPORT·합의표·critic-lint 출력) · 게이트 이력 표 (§4 와 동일 형식 — 정지 시점까지 처리분).

    • 부수 정보 — 누적 domain_impact 가 있으면 "도메인 지식 환류 제안 (누적)" 표 (knowledge-sync.md § run-cycle — 표만 여기 두고 기록 여부는 3 의 마지막 질문에 한 줄로 덧붙여 한 번에 묻는다) · wrapper 가 보고한 드리프트 후보 등 참고 사항.

    • 다음 행동 블록 — 고정 문형. 내용은 references/stop-remediation.md 의 해당 사유 행 ("결정 필요"·"대행 호출" 두 열) 에서 가져온다 — 정지가 실제로 발생한 시점에 Read 한다 (정지 없이 완주하는 호출에서는 읽지 않는다).

      ⏹ run-cycle 정지 — #{N} {slug} · {사유}
결정 필요:
  {조치표 "결정 필요" 열 — 항목별 1줄. 사용자가 판단할 내용이지 절차 목록이 아니다}
다음 행동 (하나 선택):
  a) "진행" → 제가 {조치표 "대행 호출" 열} 실행 → 완료 후 `/dp-skills:run-cycle {동일 인자}` 재실행이 재개
  b) 다르게 → 결정 내용을 말씀 주시면 반영 (후속 호출에도 남길 결정은 `/dp-skills:focus` 기록)
  c) 중단
어느 쪽으로 할까요?
      • 사용자 대면 어휘 제한 — 본 스킬 절 번호 (§2.1)·에이전트 절차 번호 (절차 10)· 내부 상태 어휘 (합의표 status 갱신·재개 판정·게이트 스텝) 를 쓰지 않는다. 산출물 경로·@ag-* 호출명·사용자에게 이미 보인 도구 출력의 도구명은 허용.
      • 마지막 줄은 답 하나를 요구하는 질문이다 — "원하시면 말씀해 주세요" 류 개방형 문장으로 끝내지 않는다.
      • "진행" 은 a) 의 확인 1회다 — 대행 호출을 실행하고 결과를 보고한 뒤 멈춘다. 재개는 사용자의 /dp-skills:run-cycle 재호출이다 (자동 재진입 아님 — description 의 자발 발동 금지 유지). 부분집합·--gated 인자는 블록에 그대로 적어 재실행 시 복원되게 한다.

    금지 — /dp-skills:fix-review 는 본 정지의 처방이 아니다 (CODE REVIEW REPORT 전용). OQ 게이트 정지는 /dp-skills:focus 로 안 풀린다 — plan-validate 의 oq 검증은 feature 체크박스·plan 마커만 본다.

    4. 큐 완료¶

    모든 feature READY → 완료 요약 + 게이트 이력 표 (사후 감사 뷰) 출력:

    | feature | critic (blocking/suggestion/nit) | retry | verdict |
| ------- | -------------------------------- | ----- | ------- |
| #3 slug | 0 / 2 / 1                        | 0     | READY   |
| #4 slug | 0 / 0 / 0                        | 1     | READY   |

    누적된 domain_impact 항목이 있으면 "도메인 지식 환류 제안 (누적)" 표를 출력하고 기록 여부를 질의한다. 승인 시 knowledge-sync.md § 기록 을 수행한다 (항목 5건 이상이면 /dp-skills:discover 재실행 권장).

    Do-NOT¶

    • feature 병렬 진행 금지 — 한 번에 1 feature (.focus.md·STATE.md 싱글톤· generator 파일 충돌 회피). 단계 단위도 동일 — wrapper 는 동기 호출이며, 직전 산출물 수신 전 다음 단계 기동은 무검증 진행이다.
    • 무검증 자동 통과 금지 — critic-lint 통과 + 합의표 blocking 0 없이 generator 진행 금지. critic 스킵 금지 (HOTL 에서 critic 은 필수 판정자다). NOT_READY· wrapper 비정상 종료 자동 통과 금지.
    • NOT_READY 재시도 1회 초과 금지 — 재실패는 정지 (수렴 루프 금지).
    • 재개 게이트 통과가 재개 지점을 앞당기는 것 금지 — §2.1 판정 지점이 우선 (구현 완료 feature 의 generator 재실행 = 이중 적용).
    • wrapper 호출 시 대상 feature 미명시 금지 — critic·generator·evaluator 세 호출 모두 번호·slug·plan 경로를 프롬프트에 넣는다 (§2.3~§2.5). 대상 추론을 wrapper 에 떠넘기지 않는다.
    • READY .eval.md 가 있는 feature 의 사이클 재실행 금지 — 체크박스 보정만 (§2.1). 재작업이 필요하면 사용자가 산출물을 지우고 재실행한다.
    • --gated 시 종전 게이트 전부 복원 — plan 사전 승인·재개 재승인을 생략하지 않는다 ([orchestration: hotl] 마커도 넣지 않는다).
    • 정지 후 뒤 feature 자동 진행 금지.
    • 상태 파일 생성 금지 — 큐·진행·재시도 카운트는 project.md + 산출물 + 세션 컨텍스트에서 파생.
    • 수동 사이클·@ag-* 동작 변경 금지 — 본 스킬은 호출 순서와 오케스트레이션 마커만 관리한다.
    • feature 마다 domain_impact 질의로 정지 금지 — 누적 후 큐 종료 시 일괄 질의.
