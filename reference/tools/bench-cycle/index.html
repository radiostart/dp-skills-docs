    bench-cycle.py¶

    dp-skills bench-cycle — 플러그인 자체 (스킬·에이전트) 가 만든 산출물을 블라인드로 전후 채점하는 사이클의 상태 기계.

    evaluator 는 코드가 요구사항을 충족하는지를 본다. 이 사이클은 에이전트가 쓴 문서 (plan.md · .plan.critic.md · .eval.md) 가 좋아졌는지를 같은 잣대로 두 번 재서 차이를 센다 — 스킬·에이전트 파일을 고친 뒤 채택할지 되돌릴지의 근거다. 사이클은 workspace/{TEAM}/bench/NNN-{slug}/ 에 살고, 단계 전이의 조건을 기계가 센다.

    지키는 것은 넷이다 — 「블라인드」의 기계 정의.

    1. 허용 목록 밖을 읽은 채점은 받지 않는다 — brief --phase X 가 그 단계의 채점자가 읽어도 되는 파일 목록을 적고, ingest 는 채점 파일 프런트매터 inputs: 를 그 목록과 대조한다. 이 사이클의 다른 채점 · 개선 계획 · 대조 · 지표 · 답 원문 · 상태 파일 · 다른 사이클 · 대화 기록은 항상 금지다. inputs: 는 자기 신고라 완전한 강제가 아니다 — 사고 방지와 사후 대조 (verify-blind) 다.
    2. 전후는 같은 잣대다 — brief --phase before 때 scenario.md·rubric.md 해시를 굳히고, after 의 brief·ingest 는 해시가 같을 때만 받는다. 잣대 값 (scorers·noise_band·disagree_gap) 도 init 때 상태에 굳힌다.
    3. 채점자는 둘 이상이고 서로 다르다 — 단계마다 scorers 명의 서로 다른 scorer: 번호가 있어야 하고, 같은 축에서 disagree_gap 이상 벌어지면 평균 대신 「불일치」로 적는다.
    4. 전후 대조는 도구가 센다 — compare 가 축 평균 차이를 noise_band 로 가르고 compare.md 를 쓴다. 적용 (applied) 과 채택·되돌림 (decide) 은 사용자 답 원문이 inputs/ 에 있어야 받는다.

    dp-skills 고유 결정 둘: - 표본은 사본이다. init·brief 는 표본·참조·대상 파일을 사이클 안 samples/ 로 복사하고 허용 목록·좌표·지표는 사본을 가리킨다. projects/ 산출물은 git 미추적이고 재호출마다 덮어쓰여 원본 참조로는 좌표가 고정되지 않는다. after 표본이 before 표본과 내용이 같으면 (sha256) 거절한다 — 같은 경로라도 다시 만든 파일이면 전후다. 대상 파일 사본도 판마다 뜬다 — init 은 변경 전 (samples/plugin/), applied 는 적용 커밋 (samples/plugin-after/). 과정 축 (P) 은 그 산출물을 만든 판의 wrapper 와 대조해야 해서, after 채점자는 뒤의 것만 받는다. - 채점자는 자기가 어느 단계인지 모른다. init 이 단계별 무작위 라벨 둘을 정해 상태에만 적고, 표본·대상 파일 사본 (samples/{라벨}/) · 지시 (brief-{라벨}.md) · 채점 파일 (scores/{라벨}-{k}.md · 프런트매터 label:) · 집계가 라벨을 쓴다. 지시에는 시나리오 § 3 의 성공·되돌림 조건을 싣지 않고 scenario.md 도 허용 목록에서 뺀다 — 기대를 아는 채점은 그 기대 쪽으로 기운다. 라벨 키가 없는 옛 사이클은 종전 이름 (before·after·samples/plugin*) 으로 끝까지 간다. - 대상 파일은 플러그인 레포에 있다. applied 는 --plugin-repo (또는 _common/config.md bench_plugin_repo) 의 git 에서 적용 커밋의 바뀐 파일을 plan.md § 2. 변경 집합 (플러그인 레포 상대 경로) 과 대조한다. CLAUDE_PLUGIN_ROOT 는 설치 캐시라 git 레포가 아니다.

    한 호출이 한 단계만 넘긴다. 채점 (before) → 계획 → 적용 → 채점 (after) → 대조 → 결정이 각각 사용자의 호출이고, 모든 응답의 다음 이 그다음 명령·멘션이다. 사이클 폴더 밖에는 아무것도 쓰지 않는다.

    단계: init → before → planned → applied → after → compared → decided → closed (어느 단계에서든 stopped)

    표본을 얻는 길은 둘이다. replay (--artifacts) 는 이미 있는 산출물을 받는다 — after 는 바뀐 판이 자연히 새로 쓸 때까지 기다린다. run (--run) 은 분리 트리 (소비 레포 최상위 링크 + workspace 사본) 에서 에이전트를 한 번씩 불러 새로 낸다 — sandbox 가 트리·단계별 플러그인 판·실행 명령을 만들고, 실행은 사용자·메인 세션이 하며, collect 가 결과를 표본으로 거둔다. 실제 산출물은 건드리지 않는다. 입력은 init 때 뜬 사본으로 심어 before·after 가 같은 입력을 받는다.

    Usage: bench-cycle.py init --slug SLUG --subject TEXT (--artifacts P [P …] | --run critic|planner --inputs P [P …]) [--context P …] [--subject-files P …] [--axes Q1,Q3,…] [--plugin-repo DIR] bench-cycle.py sandbox --id 001 --phase before|after [--dir D] · collect --id 001 --phase … bench-cycle.py sandbox-remove --id 001 --phase … [--force] bench-cycle.py show --id 001 [--for-scorer K] · list [--all] bench-cycle.py brief --id 001 --phase before|after [--artifacts P …] [--context P …] bench-cycle.py ingest --id 001 --phase before|after · verify-blind --id 001 bench-cycle.py planned --id 001 bench-cycle.py applied --id 001 --commit SHA --answer-file {cyc}/inputs/00N-answer-apply.md [--plugin-repo DIR] [--allow-extra] bench-cycle.py compare --id 001 bench-cycle.py decide --id 001 --result adopt|revert --answer-file {cyc}/inputs/00N-answer-decide.md bench-cycle.py close --id 001 [--note T] · stop --id 001 --reason T 공통: --workspace PATH (기본 ./workspace) · --team NAME (기본 workspace/TEAM.md 첫 줄)

    설정 (선택 · workspace/_common/config.md 또는 {TEAM}/context/team.config.md 의 ## 언어·도구 기본값 표): bench_scorers (2) · bench_noise_band (0.3) · bench_disagree_gap (2) · bench_stale_days (14) · bench_plugin_repo (없음)

    Exit: 0 — 성공 · 1 — 상태 오류 (게이트 거절 · 블라인드 위반 · 해시 불일치) · 2 — 사용 오류 (workspace·TEAM.md 부재 · 인자)
